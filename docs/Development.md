# Development

This page covers the public setup, repository layout, and common maintenance commands for contributors.

The distribution package is `arkive-compact`, the repository is `https://github.com/imarshallwidjaja/magic-compact`, and the runtime command remains `/magic-compact`.

## Requirements

- Bun
- Node.js 24 (the CI and release workflows use it)

## Setup

Install dependencies from the repository root:

```bash
bun install
```

CI and release workflows install with `bun install --frozen-lockfile`. Run the same command locally to confirm `bun.lock` matches the manifests.

`bun install` also runs the root `prepare` script, which sets Git's `core.hooksPath` to `.githooks`. The `pre-commit` hook runs `scripts/check-staged-format.ts`, which checks the staged content of added, copied, modified, renamed and type-changed regular files with Prettier, then runs `bun run typecheck` and `bun run lint`. The format check writes the index that `git commit` hands the hook (`GIT_INDEX_FILE`) to a temporary directory and takes file content, Prettier configuration, `.editorconfig` and the `.gitignore` and `.prettierignore` ignore files from that snapshot, so unstaged edits to any of them change nothing; it removes the directory afterwards and changes no file in the repository. A failure lists the files to format and stage again. Typecheck and lint read the working tree, so unstaged edits affect their result. The hook runs no tests; CI's four commands remain the merge gate.

## Repository Layout

### `packages/`

- `packages/opencode-plugin` - OpenCode plugin implementation for OpenCode 1 and OpenCode 2.
- `index.ts`, `tui.ts` (package root) - re-export the dual server and TUI entries for OpenCode 2's plugin-directory loader, which reads the root module rather than `exports`.
- `src/index.ts` - the package's dual default export `{id, server, setup}`; each function lazily imports its host module.
- `src/host-v1.ts` - OpenCode 1 server plugin: config hook (summarizer agent, listener identity agent, commands), slash-command handlers, native compaction guard, the `chat.params` hook that asks for every turn's reasoning on owned summary and generation forks on the verified OpenAI route, media message transform, stats events and `read_omitted_content`.
- `src/host-v2.ts` - OpenCode 2 `setup`: summarizer agent update, commands, `read_omitted_content`, the `StructuredOutput` response tool (advertised and executable only in a per-turn generation session this process owns) and the `SessionSummary` tool (only in a structured session summary session it owns), the `context`/`compaction`/`generate`/`title` hooks (owned-session controls, media projection for every request, and the readable-reasoning projection in owned requests), and stats from `session.step.ended` events.

The semantic tool `state.time.compacted` bit survives snapshot normalization, so a concurrent change to it counts as drift while `start`/`end` timing churn does not. The at-rest read runs before planning and again just before the successor is marked ready.
- A pending revert is an at-rest refusal: a successor cannot know whether the user meant to keep or discard the reverted suffix. The at-rest check also refuses a running native compaction (`time.compacting`), unfinished assistant messages, pending or running tool parts, `busy`/`retry` or unknown statuses anywhere in the `session.children` tree, and pending permissions or questions in that tree. The unfinished-assistant and tool-part test covers every stored message; the refusal names only the first such record (message ID, plus tool name, call ID and state for a tool call) and counts the rest, rendered through `boundedLabel` in `src/policy/successor.ts`. Keep it content-free: never add tool input or output, prompts, reasoning, error bodies or metadata. The public host API cannot tell an abandoned record from live work, so compaction and trimming add no normalization, staleness heuristic or bypass; improve the message instead. The one exception is `/magic-recover`, where the user declares the records abandoned: keep it a separate explicit command that applies every live check, closes records only with the host's native interrupted form, refuses what has none, and never feeds trim or compact. Never infer abandonment from age or idleness. The at-rest check accepts recovery's never-delivered launch mark and nothing else recovery writes; closed records pass because they are closed. The refusal leads with the outcome and next step and puts the references in a trailing `Record:` line; keep it under about 600 characters with every label at its cap, because the failure toast cuts text at 700. Recheck these fields and the `session.status` value set on OpenCode or SDK upgrades.

## Release

Release versions are exact numeric triplets in `X.Y.Z` form. The release helper bumps the `packages/opencode-plugin/package.json` manifest when needed, creates a `vX.Y.Z` tag on the commit whose manifest has that version, and pushes `main` and the tag. The release workflow publishes the public `arkive-compact` package with provenance and explicit public access. Publishing uses npm Trusted Publishing: GitHub OIDC via the workflow's `id-token: write` permission authenticates to the npm trusted publisher configured for GitHub user/repo `imarshallwidjaja/magic-compact`, workflow filename `publish-opencode.yml`, with npm publish permission and no environment. The workflow requires no long-lived npm token. The existing `NPM_TOKEN` GitHub Actions secret is now unused; delete and revoke it only after a future OIDC-backed publish succeeds, keeping rollback available until live verification. There is no build step because the package publishes its TypeScript source.

### Normal release

The normal release path is the tag-triggered GitHub Actions workflow:

1. Switch to `main` and integrate the `main` of origin's push repository, the `<push-url>` described below, so that local `main` contains it: run `git fetch <push-url> refs/heads/main`, note the SHA that `git rev-parse FETCH_HEAD` prints, and merge that SHA. `origin/main` tracks the fetch repository, which may differ. Leave the index and working tree clean, with no untracked files.
2. Run the checks documented under Common Commands, including the full plugin suite, and confirm the `Check` workflow passed on the current `main` commit. The release commit that the helper adds changes only the manifest version and `bun.lock`.
3. Confirm npm Trusted Publishing is configured for `imarshallwidjaja/magic-compact` with workflow `publish-opencode.yml`, npm publish permission, and no environment; the workflow needs no npm token.
4. Invoke `bun run release-opencode -- X.Y.Z`.
5. Monitor both workflows. The push of `main` runs `Check` on the release commit. The tag runs the publish workflow, which reruns the same four checks on the tagged commit before `npm publish` and then creates the GitHub Release.

Here `origin` means the repository that `git remote get-url --push --all origin` names, after Git applies `pushurl`, `insteadOf` and `pushInsteadOf`. It may differ from the fetch URL, for example an SSH push URL beside an HTTPS fetch URL, but it must be exactly one URL. Git reads a bare word such as `upstream` as a remote when a remote of that name exists, including a legacy `.git/remotes` or `.git/branches` file, so the helper writes a relative local path as `./upstream`; URLs, `host:path` forms and absolute paths stay as they are. That literal is the `<push-url>` used below. Git must read `<push-url>` as no remote and must not rewrite it again when it is given to `ls-remote`, `fetch` or `push`.

The helper resolves `<push-url>` once and reads from and pushes to it, so a later change to `remote.origin.pushurl` does not change the destination. `npm version`, `bun install` lifecycle scripts and the repository's Git hooks run during the release and can change other configuration, HEAD or refs. The helper therefore checks again, after the version bump, after the release commit and after the tag, that HEAD is `main` at the commit it expects and that Git still reads `<push-url>` as itself, and stops otherwise. These are fresh checks, not a lock: a change that another process makes after the last check, just before the push, still applies, as it would to any Git command. Keep one writer in the repository during a release.

Before it writes any file, commit or ref, the helper refuses unless HEAD is the branch `main`, the index and working tree are clean with no untracked files, `vX.Y.Z` exists neither locally nor on `origin`, origin has one push URL as described above, and local `main` contains `origin`'s `main`. It checks the exit status of every Git read before it uses the output, so a failed read refuses with a fixed message instead of passing for a clean tree or another version, and it reads the working tree state without optional locks, so a refusal leaves the index file byte for byte as it was. It records the commit that `main` names and works from that commit. When the manifest version committed there differs from `X.Y.Z`, it runs `npm version` and `bun install`, refuses with no commit if anything other than `packages/opencode-plugin/package.json` and `bun.lock` changed or was staged, stages those two files, refuses again if the index or working tree then holds anything else, and records the tree of that index. It commits only those two paths as `Release vX.Y.Z`, leaving anything staged by someone else staged. The release commit must be the one commit that `main` gained and must have exactly the recorded tree, so a hook that amends the commit's content stops the release before the tag, even when the amendment stays within those two files and keeps the version. When the recorded commit already has that version, it skips the bump and releases that commit. Before tagging, it requires the manifest in the release commit to have version `X.Y.Z` and the index and working tree to match it. It tags the release commit by ID, requires the tag to name that commit, and runs `git push --atomic --no-follow-tags <push-url> <release-commit>:refs/heads/main <tag-object>:refs/tags/vX.Y.Z` with the IDs it checked, so `origin` receives exactly that commit as `main` and that tag, or neither, whatever `remote.origin.push` and `push.followTags` say. `test/release.test.ts` covers these guards against local bare repositories; no test exercises GitHub or npm.

### Interrupted release helper

The helper never stashes, resets or cleans. A rerun after an interruption either continues safely or refuses, and a refusal leaves the repair to the operator:

- Stopped before the release commit, for example when `npm version` or `bun install` failed, or when the bump changed or staged another file: the manifest or `bun.lock` is changed in the working tree, and may be staged, so a rerun refuses. Inspect the changes. To commit the bump yourself, first run `bun install` to completion so that `bun.lock` matches the manifest, then commit only those two files as `Release vX.Y.Z` with `git commit -m "Release vX.Y.Z" -- packages/opencode-plugin/package.json bun.lock`; otherwise restore them. Deal with any other change separately, then rerun.
- Stopped after the release commit and before the tag: a rerun finds version `X.Y.Z` at HEAD and tags it without another bump. If the helper refused because the committed version differs, other files changed, or the release commit's content differs from the checked version bump, inspect HEAD and the working tree before deciding: a rerun tags HEAD as it is once its manifest has the version.
- Stopped because HEAD left `main`, `main` moved, or Git would now rewrite `<push-url>` or read it as a remote: a script or hook that the release ran made the change, and the message says whether the bump, the release commit or the tag was left. Nothing was pushed. Find and undo the change before you continue with the matching case in this list. A rerun releases the commit that `main` then names when its manifest already has version `X.Y.Z`, so first remove any commit on `main` that you do not intend to release.
- Stopped after the tag, including a failed or rejected push: a rerun refuses because the local tag exists, and its message points here. Find `<push-url>` as described above: `git remote get-url --push --all origin` must print one URL, with `./` added in front of a relative path. Run `git ls-remote <push-url> refs/heads/main refs/tags/vX.Y.Z`. If the push repository already has the tag, it is immutable: never move, delete or recreate it. If it has no such tag, confirm that the tag names a commit whose manifest has version `X.Y.Z` (`git show 'vX.Y.Z^{commit}:packages/opencode-plugin/package.json'`). Fetch the push repository's `main` with `git fetch <push-url> refs/heads/main` and note the SHA that `git rev-parse FETCH_HEAD` prints as `<push-main>`; `origin/main` tracks the fetch repository and may differ. When `git merge-base --is-ancestor <push-main> main` exits 1, run `git merge <push-main>`; a merge keeps the tagged commit in `main`'s history without changing the tag, where a rebase would leave the tag off `main`. Before pushing, confirm that `git merge-base --is-ancestor vX.Y.Z main` and `git merge-base --is-ancestor <push-main> main` both exit 0. Then note `<main-sha>` from `git rev-parse refs/heads/main` and `<tag-object>` from `git rev-parse refs/tags/vX.Y.Z`, and push those IDs explicitly to that one URL: `git push --atomic --no-follow-tags <push-url> <main-sha>:refs/heads/main <tag-object>:refs/tags/vX.Y.Z`. The local tag was never published, so moving or deleting it instead is possible, but it is a deliberate operator decision.

### Recovery-only manual dispatch

Use manual dispatch only when an existing immutable tag was already pushed and either GitHub created no workflow run or the prior run reached a terminal failure that published nothing, the corresponding npm version is still unpublished, and no GitHub Release exists. Verify all three absences before one dispatch, then use the tag's exact 40-character commit SHA:

```bash
gh workflow run publish-opencode.yml --ref main -f release_tag=vX.Y.Z -f release_sha=<40-char-tag-commit>
```

Never move, delete, or recreate the tag. Never dispatch while a prior run is active, and never dispatch after the npm version or GitHub Release exists. After a terminal failure that published nothing, a new dispatch is allowed only after the workflow fix is reviewed and pushed, and only after the operator freshly reconfirms the unchanged tag/SHA, that the npm version is absent, and that no GitHub Release exists.

### Missing GitHub Release after npm publish

When `npm publish` succeeded but the workflow's `gh release create` step failed, the npm version exists, so neither a workflow rerun, a dispatch nor another `npm publish` is allowed. Create only the missing release, after verifying:

1. `git ls-remote origin refs/tags/vX.Y.Z` names the release SHA of the failed run, and `git show <release-sha>:packages/opencode-plugin/package.json` has version `X.Y.Z`.
2. The failed run's publish step succeeded, and `npm view arkive-compact@X.Y.Z version` prints `X.Y.Z`.
3. `gh release view vX.Y.Z` finds no release.

Then run the workflow's own command with `--verify-tag`, which aborts instead of creating a tag when `origin` lacks it:

```bash
gh release create vX.Y.Z --verify-tag --title vX.Y.Z --generate-notes
```
