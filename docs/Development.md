# Development

This page covers the public setup, repository layout, and common maintenance commands for contributors.

The distribution package is `arkive-compact`, the repository is `https://github.com/imarshallwidjaja/magic-compact`, and the runtime command remains `/magic-compact`.

## Requirements

- Bun
- Node.js 24 (the CI and release workflows use it)

## Setup

Install dependencies from the repository root:

```bash
bun install
```

CI and release workflows install with `bun install --frozen-lockfile`. Run the same command locally to confirm `bun.lock` matches the manifests.

## Repository Layout

## Common Commands

- `bun run typecheck` - TypeScript type checking in two passes: `tsconfig.json` for `packages/*/src`, then `tsconfig.eval.json` for the compaction and decision eval sources (`eval/compaction`, `eval/decisions`) and their canonical tests (`test/compaction-eval.test.ts`, `test/decision-eval.test.ts`). The eval pass maps the wrapper's `arkive-compact-eval-subject` alias to this checkout's plugin entry.
- `bun run lint` - ESLint checks.
- `bun run format` - Prettier formatting.
- `bun run format:check` - Prettier check without writing. It checks only Git-tracked files (`git ls-files`), so ignored scratch directories and local config are skipped; `.prettierignore` still excludes vendored and license files, and unknown file types are ignored.
- `bun test packages/opencode-plugin/test` - full plugin suite. Tests use fakes and in-memory SQLite, so they need no `TYPESAFE_API_KEY` or network.
- `bun test packages/opencode-plugin/test/compact.test.ts` - focused compaction suite.
- `bun test packages/opencode-plugin/test/trim.test.ts` - focused trim suite.
- `bun test packages/opencode-plugin/test/retention.test.ts` - focused retention classifier suite.
- `bun run eval:compact check` - validate the frozen compaction evaluation corpus and its plans offline. `bun run eval:compact run --server http://127.0.0.1:4096 --model provider/model#variant --out DIR --dry-run` runs preflight on a local OpenCode server without creating a session or calling a model; a run without `--dry-run` makes paid summarizer requests. See `docs/CompactionEvaluation.md`.
- `bun run eval:decisions check` - validate the bundled decision evaluation pack offline. `bun run eval:decisions run --provider jev --model jev-1.14.0 --dry-run` prints a run plan without a key or network; a run without `--dry-run` makes paid requests. See `docs/DecisionEvaluation.md`.

## Continuous Integration

`.github/workflows/check.yml` runs on pushes to `main`, pull requests, and manual dispatch. After a frozen-lockfile install it runs `bun run format:check`, `bun run typecheck`, `bun run lint`, and `bun test packages/opencode-plugin/test`. `publish-opencode.yml` runs the same four commands before `npm publish`, so a failing check stops publication. Keep the two command lists in sync.

## Notes

- The project uses Bun workspaces.
- For the user-facing plugin install flow, see the main `README.md`.
- The native-checkpoint cases in `packages/opencode-plugin/test/compact.test.ts` are maintenance canaries for user `compaction` parts with optional `tail_start_id`, and assistant `parentID`, `summary`, `finish`, and `error` fields. Check those fields against OpenCode's compaction implementation whenever OpenCode or `@opencode-ai/sdk` is upgraded.
- Retention's native-view canaries in `test/retention.test.ts` cover failed no-tail checkpoints, completed then failed checkpoints, failed/unfinished tail reordering, and two completed checkpoints with a crossing retained tail. Compare membership and order against pinned `filterCompacted`, including its final reorder independently of summary completion. Do not reuse the writer checkpoint inspector for budget/image accounting: valid native error/incomplete paths must remain available to task-aware trim. Only unresolved or nonpreceding selected tails fail this view's safety check; full stored fork identity remains checked separately.
- Source drift detection structurally compares every behavior-affecting message/part field and ordering while ignoring volatile timing fields and token/cost accounting churn, plus the continuation state a successor copies (directory, workspace, title, agent, model, permission rules, metadata). The semantic tool `state.time.compacted` bit survives snapshot normalization, so a concurrent change to it counts as drift while `start`/`end` timing churn does not. The at-rest read runs before planning and again just before the successor is marked ready.
- A pending revert is an at-rest refusal: a successor cannot know whether the user meant to keep or discard the reverted suffix. The at-rest check also refuses a running native compaction (`time.compacting`), unfinished assistant messages, pending or running tool parts, `busy`/`retry` or unknown statuses anywhere in the `session.children` tree, and pending permissions or questions in that tree. The unfinished-assistant and tool-part test covers every stored message; the refusal names only the first such record (message ID, plus tool name, call ID and state for a tool call) and counts the rest, rendered through `boundedLabel` in `src/policy/successor.ts`. Keep it content-free: never add tool input or output, prompts, reasoning, error bodies or metadata. The public host API cannot tell an abandoned record from live work, so do not add normalization, staleness heuristics or a bypass; improve the message instead. The refusal leads with the outcome and next step and puts the references in a trailing `Record:` line; keep it under about 600 characters with every label at its cap, because the failure toast cuts text at 700. Recheck these fields and the `session.status` value set on OpenCode or SDK upgrades.
- Resolve the plugin-owned `magic-compact-summarizer` agent's configured model/variant and matching provider descriptor once; never fall back to the native `compaction` agent or the source model. The config hook keeps an operator-configured `model` and `variant` on that agent and owns its description, mode, hidden flag, prompt, and deny-all permission. Derive the 32K maximum half-output target, usable input, 400K/80% normal target, 90% hard single-turn limit, 500K/90% halo limit, and 8K fixed reserve in `compact/batch.ts`, which plans exactly one target turn per batch. The 8K reserve is only for non-explicit host, system, and provider overhead. Separately tokenize each complete rendered explicit request exactly once for every normal, usable, hard-turn, and halo decision: static instructions, byte-identical global index, local target JSON and punctuation, fixed-shape conservative markers plus injected marker text, exact ordinal digits, and media counts. Use the 32K fallback output limit only when the descriptor lacks a safe positive output value. Estimate ordinary visible strings through `countGptTokens`. Charge only image/PDF-typed file parts and completed non-compacted tool attachments 8K; ignore `text/plain` and directory file parts as non-model-visible, and estimate other model-visible file parts and attachments by their URL (encoded length for `data:` URLs, tokenized text otherwise). Estimate arbitrary or nested `data:` tool strings by their encoded length without invoking the tokenizer on their payloads. Match the pinned `message-v2.ts` compacted, error, interrupted-output, pending, and running state branches exactly.
- Build one immutable global index before batching from all complete turns in the planner's post-native-checkpoint effective source range. Include target candidates, opaque summary-bearing turns, and retained-tail complete turns; exclude the trailing active incomplete turn. Entries contain exactly `sourceOrdinal` and the first ordinary non-synthetic/non-ignored user text line capped at 160 characters. `sourceOrdinal` is the one-based complete-turn position in full source order and is distinct from target candidate ordinals.
- Plan one batch per candidate in chronological order and never split a turn. Every generation request owns exactly one target turn: multi-target requests produced wrong result counts live because OpenCode does not enforce the response schema, so do not reintroduce packing. Render the complete request and response protocol for that single target; a target above the normal target keeps the hard single-turn limit. Run at most five independent batches concurrently. Each batch gets a fresh complete source fork with an ordered session rule that denies operational tools and allows only the injected `StructuredOutput` response tool, full rewritten-shape verification, sequential bounded `session.deleteMessage` calls for every unrelated message, and an exact retained-history reload before markers. Before deletion, capture the retained rewritten message/part IDs, order, roles, parent links, part types, and fork-scoped references; reject any substitution, reorder, or link change on reload. Retain the complete target turn plus at most the one complete preceding non-checkpoint turn, only when native history plus the complete request stays within the halo limit. Never retain a later turn, including turns protected by `N`; the global map keeps their user anchors. Never use part deletion for generation isolation or issue more than one prompt on a fork.
- Plan with `NATIVE_BATCH_PLANNING_NONCE`, whose 22 ASCII bytes each tokenize separately under the pinned tokenizer and therefore conservatively represent a valid 22-byte nonce body. Before any fork creation, allocate every unique crypto-quality 128-bit nonce absent from source, render the immutable real prompt, and require its exact explicit-request and response-protocol counts not to exceed the conservative records or the batch's normal, hard, halo, usable-input, and output limits. Recheck the nonce against rewritten retained fork strings before marker insertion. Keep target candidate ordinals in every marker, exact target prompt index, and response. Batch-array order is the final chronological mapping. Validate every response and exact target coverage. Every batch derives its byte-identical global index, target index, fork plan, and estimate from the same pre-generation source; never feed generated summaries into another request. The first failure stops new admission; drain every already-active batch, collect all sanitized failures in deterministic batch order, clean every fork, and accept no generated result until all batches pass. Generation completes before any successor is created. Magic Compact makes one `session.prompt` call per fork and adds no plugin-level provider or model retry, adaptive splitting, or model fallback; OpenCode may apply its runtime provider/transport retry policy or additional model steps required by structured-output processing. Partial writes remain unsupported.
- Keep each exact target index proportional to its target count. Each target entry contains only the exact fork marker, target ordinal, and expected user-and-assistant inline-image count. Precede it with the byte-identical `{globalTurnIndex: [{sourceOrdinal, anchor}]}` orientation map. Require every response item to have exactly `ordinal`, `marker`, `summary`, and `visualDescriptions` and to echo its exact marker and target ordinal in order. Global anchors are orientation-only; never make the model echo user text as response identity. Reject only the active exact generation nonce or marker token inside summaries and visual descriptions, then discard marker identity before persistence. Never serialize SDK records, message/part refs, assistant traces, tool state, provider metadata, encrypted reasoning, data URLs, manual file parts, or generated summaries into either index.
- Await generation-fork creation and each model request without a local wall-clock deadline so the command never loses ownership of a server-side fork. Keep permission updates, message isolation/reloads, marker insertion, and every toast under the shared control-operation deadline. Once a fork ID is known, directly await provider or validation failure abort and every fork deletion; cleanup rejection is surfaced, every started batch drains before command settlement, and every session that could not be deleted is named in the aggregate (`ForkCleanupError` and `V2GenerationError` carry `undeletedSessionIDs`). `/magic-compact` and `/magic-trim` show a long-lived view-only progress toast before slow work, then send terminal no-op, success, or failure feedback. If a timed-out progress delivery later settles, reassert the terminal toast without awaiting that reassertion in the command. Toast rejection or timeout never changes operation or recovery outcomes and never creates conversation, model-input, stats, or omission-cache data. OpenCode exposes no later delivery signal after the client promise rejects, so a progress toast applied remotely after that rejection cannot be detected or corrected. Native overflow reports trim-first guidance. A configured model input budget too small to fit the fixed 8K reserve or the mandatory repeated global index fails before any fork with trim-first/model-capacity guidance. An output limit requires a model with more output capacity because every request covers a single turn. A throttling error returned by OpenCode is a normal plugin failure, not a Magic Compact retry signal; OpenCode may apply its runtime provider/transport retry policy before the prompt call returns.
- Compact and trim never write the source session. They build the successor history by applying closed edits (prepend part, replace part, delete part, delete message, append message) to a clone of the exact source records, then replay it onto a new session created with the source's continuation state. A no-op creates no successor. Before the ready update, a failed candidate is deleted only when a fresh read shows a prefix of the planned history; otherwise it is kept and named. After the ready update is sent, a failure keeps it.
- Each batch calls `session.prompt` once with the fixed JSON-schema `format`, whose `turns` array sets `minItems` and `maxItems` to 1. The prompt text states the same exact count. OpenCode 1.18.30 injects its side-effect-free `StructuredOutput` response tool for the JSON-schema request and returns its captured object on assistant `info.structured`; the injected tool still passes through the host's final merged-permission tool filtering, where the last matching rule wins. The fork's ordered session rule therefore ends with an exact `StructuredOutput` allow after the wildcard deny, which keeps the host response tool while every operational tool stays denied. Text parts are never parsed as a fallback. The installed 1.18.30 prompt path does not use `retryCount`, so the request omits it. Magic Compact adds no plugin-level provider or model retry or fallback; OpenCode may apply its runtime provider/transport retry policy or additional model steps required by structured-output processing. Charge the fixed schema JSON that every request transmits against explicit input, and keep the host-injected system instructions in the 8K non-explicit reserve. Budget estimated summary/description content plus the mandatory envelope and array/object punctuation, echoed marker, ordinal, `summary` property, and every `{ordinal, description}` visual entry before packing. The schema states the single-result count, stable keys, types, and required fields to the model, but it is guidance rather than enforcement: OpenCode 1.18.30 wraps it with the AI SDK `jsonSchema()` helper without a validator, so tool arguments are not checked against it locally, and it sends `strict: false` on every function tool for `@ai-sdk/openai`, `@ai-sdk/azure`, and `@ai-sdk/amazon-bedrock/mantle` providers. Local validation is authoritative and still requires exactly one result, its target ordinal, exact marker echo, nonempty summary, and exact visual coverage. Reject active nonce leakage before framing, then require complete target-ordinal coverage across all batches. Validation failures expose only fixed categories (missing structured output, invalid envelope, turn count mismatch, turn shape/identity, summary, visual coverage, nonce leakage) through lifecycle and batch errors; turn count mismatches carry only the expected and received integers, and turn shape/identity failures carry only the first failed check (`shape`, `ordinal`, or `marker`) and its target ordinal. - Fork chronology is pinned to OpenCode 1.18.30 at `830d5eb535`. `Session.fork` copies records one at a time, minting each message and part ID from `Date.now() * 4096` plus a counter that resets whenever the millisecond value changes. Parts are read back in ID order and messages by immutable row `time_created`, then ID. A host clock that steps backwards while a native fork is copied therefore reverses an otherwise valid history even when the source timestamps are monotonic, and JSON creation times that disagree with row times reorder messages the same way. `forkSession` never lets that copy populate a fork. It validates the planned history (session ownership, unique message and part IDs, safe creation times, and parent and compaction-tail references that resolve strictly before the referencing message) before any host call, creates the fork cut exclusively before the first planned message (no cut for an empty history), requires the persisted fork to be empty, and writes the history once with `sync.replay`: consecutive version-1 append events after the native `session.created.1` at sequence zero, IDs minted from one clock reading and an ordinal counter, and each message first seeded with an ordered row key and then updated to restore its exact JSON info, because the message projector updates only JSON on an existing row. The persisted reload must equal the planned history exactly (order, IDs, links, content, timestamps), and the live source must still match the normalized plan before the fork is usable. An empty history skips replay, because the host rejects an empty event list, and keeps the live-source recheck. On host upgrades recheck these contracts, the SDK's `sync.replay` routing, and the host's decoding of replayed records: a record the host stores with dropped or altered fields fails the exact reload check and is never repaired. Never replace this with sorting only the loaded array, which would leave native model input and backup recovery misordered.
- `forkSession` gives each history read it performs (empty-cut check, replayed reload, live-source recheck) at most two attempts, each with a fresh `attemptWithinDeadline` window of the existing `controlTimeoutMs` (30 seconds by default). Retry covers a timed-out or rejected request, including an error response, only; a successful response that is not an array, mismatches, or fails identity/link checks is terminal and never re-read. Do not add sleeps, configuration, queues, or retries around fork creation, replay, cleanup, or provider requests. `ForkHistoryError.reason` is a fixed union whose `detail` text is content-free (`history read timed out`, `history read failed`, `history read returned invalid data`, `fork was not empty`, `history replay failed`, `replayed fork did not match the plan`, `source history was invalid`, `source history changed`, `host returned an invalid fork`); `ForkCleanupError` keeps the primary reason, and generation, retention and backup errors include the detail. Keep new reasons free of host bodies, paths, IDs, and values.

## Release

Release versions are exact numeric triplets in `X.Y.Z` form. The release helper bumps the `packages/opencode-plugin/package.json` manifest when needed and creates a `vX.Y.Z` tag. The release workflow publishes the public `arkive-compact` package with provenance and explicit public access. Publishing uses npm Trusted Publishing: GitHub OIDC via the workflow's `id-token: write` permission authenticates to the npm trusted publisher configured for GitHub user/repo `imarshallwidjaja/magic-compact`, workflow filename `publish-opencode.yml`, with npm publish permission and no environment. The workflow requires no long-lived npm token. The existing `NPM_TOKEN` GitHub Actions secret is now unused; delete and revoke it only after a future OIDC-backed publish succeeds, keeping rollback available until live verification. There is no build step because the package publishes its TypeScript source.

### Normal release

The normal release path is the tag-triggered GitHub Actions workflow:

1. Verify that `packages/opencode-plugin/package.json` has the intended `arkive-compact@X.Y.Z` version.
2. Run the checks documented under Common Commands, including the full plugin suite, and confirm the `Check` workflow passes on the release commit. The publish workflow reruns these checks before `npm publish`.
3. Confirm npm Trusted Publishing is configured for `imarshallwidjaja/magic-compact` with workflow `publish-opencode.yml`, npm publish permission, and no environment; the workflow needs no npm token.
4. Invoke `bun run release-opencode -- X.Y.Z`.
5. Monitor the tag-triggered publish and GitHub Release workflow.

### Recovery-only manual dispatch

Use manual dispatch only when an existing immutable tag was already pushed and either GitHub created no workflow run or the prior run reached a terminal failure that published nothing, the corresponding npm version is still unpublished, and no GitHub Release exists. Verify all three absences before one dispatch, then use the tag's exact 40-character commit SHA:

```bash
gh workflow run publish-opencode.yml --ref main -f release_tag=vX.Y.Z -f release_sha=<40-char-tag-commit>
```

Never move, delete, or recreate the tag. Never dispatch while a prior run is active, and never dispatch after the npm version or GitHub Release exists. After a terminal failure that published nothing, a new dispatch is allowed only after the workflow fix is reviewed and pushed, and only after the operator freshly reconfirms the unchanged tag/SHA, that the npm version is absent, and that no GitHub Release exists.
