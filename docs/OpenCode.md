# OpenCode Behavior Specification

OpenCode-specific runtime behavior. Core behavior and safety guarantees live in [`Core.md`](Core.md).

## Hosts

One `arkive-compact` package serves OpenCode 1 (1.18.30 and later 1.x) and OpenCode 2 (2.0.28). Its default export is one object, `{id: "arkive-compact", server, setup}`: OpenCode 1 calls `server(input, options)` and OpenCode 2 calls `setup(context)`. Each function imports its host module (`src/host-v1.ts` or `src/host-v2.ts`) only when called, so neither host loads the other's plugin API. The `./server` export and the package root resolve to this object; OpenCode 2 loads a plugin directory from its root `index.ts`, which re-exports it. The TUI companion follows the same shape (`{id: "magic-compact", tui, setup}` from `./tui` and the root `tui.ts`).

Both hosts run the same policy: request-turn grouping and ranges, the tool rules, task-aware retention candidates and decisions, the generation prompt, markers, nonce, response schema and strict validation, summary framing, batch budgets, profitability and the savings gate. Each host adapter owns its native records: it maps them onto the policy's views and applies the resulting edits to clones of its own records, never converting one host's records into the other's. The sections below describe OpenCode 1 unless they say otherwise; [OpenCode 2](#opencode-2) lists where OpenCode 2 differs.

## Commands

- `/magic-compact [N]` writes a compacted copy of the current root session to a new successor session.
- `/magic-trim [N] [--heuristic]` writes a copy with historical tool I/O trimmed, without summarizing messages, to a new successor session.
- `/magic-stats` injects an ignored stats notice for the current session.
- `read_omitted_content` is registered as an OpenCode plugin tool.

`/magic-compact` accepts only a non-negative integer argument. `/magic-trim` accepts at most one non-negative integer and at most one exact `--heuristic` flag, in either order; any other token or a duplicate fails before any work. `/magic-stats` accepts no arguments.

Every command first connects to OpenCode's public HTTP API through the `@opencode-ai/sdk/v2/client` factory, using the plugin input's `serverUrl` and `directory` plus basic auth from `OPENCODE_SERVER_PASSWORD` and `OPENCODE_SERVER_USERNAME` (default `opencode`) when a password is set. The supported host floor is OpenCode 1.18.30. The plugin's config hook registers a disabled `magic-compact-listener-identity` agent whose description carries a random per-process value; a disabled agent never reaches provider requests or the task tool's subagent list. A command proceeds only when `config.get` over that connection returns the same value under the control deadline. Otherwise it throws listener startup guidance (`opencode --port 0`, or `opencode serve` with `opencode attach`) before any session read or write. OpenCode without a listener reports a default `serverUrl` that another process may own, which is why identity, not reachability, decides. The value is never written to operator config files.

Both `/magic-compact` and `/magic-trim` read `TYPESAFE_API_KEY` and the optional `MAGIC_COMPACT_KEEP_THRESHOLD_PERCENT` from the OpenCode server process environment when the command runs, and derive the retention policy once, after argument validation and before connecting to the server. `/magic-trim --heuristic` never reads or validates either. Command handlers throw success, no-op, or validation messages so OpenCode does not continue sending the slash command to the LLM.

After argument and execution-option validation, compact and trim show a long-lived `Compacting session...` or `Trimming session...` TUI toast before slow work, then send terminal feedback. If a timed-out progress delivery later settles after terminal feedback was sent, Magic Compact best-effort reasserts the terminal toast. These toasts are view-only: they do not append messages, enter model input, change stats, or create omission-cache entries. Delivery is bounded by the shared control deadline and cannot change the command outcome. Terminal success feedback and the thrown success message name the successor session ID. OpenCode 1.18.30's HTTP API replaces a thrown command error with a generic error and a reference whose message appears only in the server log, so a headless client finds the successor through the `tui.toast.show` event or by listing root sessions whose `metadata.magicCompact.successorOf` names the source and whose `ready` is `true`. OpenCode exposes no later delivery signal after the client promise rejects, so Magic Compact cannot detect and correct a progress toast that the host applies after such a rejection.

Because OpenCode 1 shows a thrown command error to no client, every compact or trim failure is reported as one `Magic Compact Failed` or `Magic Trim Failed` error toast, shown for 50 ms per character of its text, at least 8 seconds, and the original error is still thrown for the server log. The text is cut at 700 characters, so a toast stays up at most 35 seconds. A failure before execution (argument parsing, the keep-threshold variable, or the listener identity check) has no verified listener yet, so its toast goes through the plugin input's own `client`. In OpenCode 1.18.30 that client calls this instance's server in process unless the instance's own listener was already running when plugins loaded, in which case it uses that listener; it never falls back to the default `serverUrl` that another process may own. Execution failures, progress, no-op and success toasts go through the verified listener only, so no failure is reported twice. `commandFailureMessage` in `src/commands.ts` writes the text for both hosts: the message of an error the plugin marked as its own (`src/policy/feedback.ts`: the `PluginMessageError` base, or `markPluginMessage` for an `AggregateError`) without its class name, plus a `Details: stage <stage>[, HTTP <status>][, <code>].` line for a successor failure. Any unmarked error, whatever its type or fields, becomes `<command> stopped on an unexpected error (HTTP <status>, <code>). The original session was left unchanged. Retry; if it fails again, check the OpenCode server log.` with only the classified status and allowlisted code. This includes a dependency's plain `Error`: the tokenizer throws `Disallowed special token found: <|endoftext|>` for a literal special token in tool output, and that text is never shown. A message the plugin marks must be fixed text, never host, dependency or session content, so a new error meant for the person running a command extends `PluginMessageError` and one that is not stays unmarked.

## Compaction Flow

1. Parse `N`; default is `0`.
2. Read the source at rest (see Successor Sessions), then validate native checkpoint artifacts and build one per-turn compaction plan from that read.
3. Stop early with a toast if no assistant turns are eligible. When `N` preserved at least one whole request turn (`preservedTurnCount` on the plan), the toast also states that count and how a request turn is counted.
4. Compute the next `compactionCount` from the source's `metadata.magicCompact.compactionCount`.
5. Count canonical model-facing active content locally with `gpt-tokenizer` and `projectManifestCoveredMedia`. Include model-facing synthetic parts, exclude ignored user reporting parts, include ignored assistant text, and retain the unprojected count for separate physical-pruning accounting. Provider usage remains telemetry only.
6. Run task-aware retention (see Task-Aware Retention) over the summarized turns that carry no Magic summary. Any retention failure ends the command here, before per-turn generation or a successor.
7. Build one immutable global orientation index from every complete turn in the planner's effective source range after native-checkpoint filtering. Include eligible targets, opaque existing-summary turns, and retained-tail complete turns; exclude the active incomplete turn. Each entry has exactly `sourceOrdinal`, the stable one-based complete-turn position in full source order, and `anchor`, the exact escaped first ordinary non-synthetic/non-ignored user text line capped at 160 characters. Then exclude every turn already containing `metadata.magicCompact.summary === true` from target candidates. For each remaining selected target, derive a separate exact index entry with a monotonic target ordinal and the count of authoritative user then assistant inline `data:` `image/*` parts. Validate generated summary/boundary part-ID availability and build each v3 media manifest locally from encounter ordinal, exact MIME, and SHA-256 of the exact URL. Tool `state.attachments` do not enter the persisted manifest.
8. Resolve the plugin-owned `magic-compact-summarizer` agent and require the model the operator configured on it. Resolve that provider/model's live descriptor once and use the configured variant; never use the source model or OpenCode's native `compaction` agent as a fallback. Set output target to `min(32_000, floor(limit.output * 0.5))` with the bounded fallback, usable input to `min(limit.input when present, limit.context - output target)`, normal input target to `min(400_000, floor(usable input * 0.8))`, hard single-turn input to `floor(usable input * 0.9)`, and halo input to `min(500_000, hard single-turn input)`.
9. Estimate each target turn without serializing messages. Tokenize ordinary visible text and reasoning through the pinned local tokenizer. Charge image/PDF-typed file parts and completed non-compacted tool `state.attachments` 8K each; ignore `text/plain` and directory file parts as non-model-visible, and estimate other model-visible file parts and attachments by their URL (encoded length for `data:` URLs, tokenized text otherwise). Treat arbitrary or nested `data:` strings in tool input, completed output, error text, and model-visible interrupted `state.metadata.output` as ordinary provider-request text, estimated conservatively by encoded length without invoking the tokenizer on their payloads. Mirror native compacted, interrupted, error, pending, and running output selection. Reserve 8K only for non-explicit host, system, and provider overhead. Separately render and tokenize the complete explicit request exactly once for every planned batch: static instructions, byte-identical global index, local target JSON/punctuation, fixed-shape marker and injected marker text, exact ordinal digits, and media counts. Charge the fixed schema JSON for the model-visible StructuredOutput tool against explicit input, including its single-result `minItems` and `maxItems`; the host-injected structured-output instruction remains in the non-explicit reserve. Output estimates add summary/description content to the mandatory response envelope, punctuation, echoed marker/ordinal fields, `summary` property, and every visual-description record. Plan exactly one target turn per batch in chronological order with no split turns; a turn above the normal target keeps the hard single-turn limit. Multi-target requests are not planned because OpenCode does not enforce the response schema and live multi-target responses returned the wrong result count. If the complete request or mandatory global index cannot fit, fail before fork creation with trim-first/model-capacity guidance. If one turn exceeds the hard limit, fail before a successor with `/magic-trim`-first guidance; if its complete estimated response exceeds the output target, require a model with more output capacity.
10. For every planned batch, retain the complete target turn plus at most the one complete preceding non-checkpoint turn, only while native history plus the complete explicit request stays within the halo limit. Later turns, including turns protected by `N`, never enter a generation request; the global map still carries their user anchors, and the successor keeps them unchanged. Reload the raw source under the control deadline and require its normalized snapshot to match the plan. Then directly await a fresh complete chronology-preserving source fork (see Fork Chronology) and apply the ordered session rule that denies operational tools and allows only the injected `StructuredOutput` response tool under the control deadline. Load and verify the full rewritten-ID chronological role/part-type shape; each history read of that fork boundary gets at most two attempts (a timed-out or rejected request only, 30 seconds per attempt by default), and a response that arrives is never re-read. Before deletion, capture the retained rewritten message IDs, part IDs, exact order, roles, parent links, part types, and fork-scoped session/message/compaction-tail references. Delete every other fork message sequentially through `session.deleteMessage`; never delete parts for generation isolation or retain distant turns merely because they appear in the global index. Reload and require that exact retained identity before markers.
11. Plan marker fields with `NATIVE_BATCH_PLANNING_NONCE`, a 22-byte fixed shape whose bytes each tokenize separately under the pinned tokenizer. Before creating any fork, choose each unique crypto-quality 128-bit nonce absent from the source, render the exact immutable prompt, and require its explicit-request and response-protocol counts not to exceed the conservative records or the normal, hard, halo, usable-input, and output limits. Recheck the nonce against rewritten retained-fork strings, then inject the nonce/target-ordinal marker only on the target's first user message. Prompt that fork exactly once through `magic-compact-summarizer` with the already-checked prompt. The one text part contains short instructions, the byte-identical `{globalTurnIndex: [{sourceOrdinal, anchor}]}` map, and the separate exact marker/target-ordinal/image-count index. The global map is orientation-only: its anchors never identify response items, and it carries no distant assistant/tool content. OpenCode's native conversion supplies only retained user, assistant, reasoning, tool output/attachments, and file media; Magic Compact never manually serializes or reattaches them. Require image capability if the union of retained batch histories may expose an image.
12. Run independent batches with maximum concurrency five. Every prompt, index, history isolation plan, and estimate derives from the same immutable pre-generation source plan; generated summaries never alter later requests. Await every model request without a local wall-clock deadline. Request `format: {type: "json_schema", schema}` with the fixed single-result schema on the one generation prompt per fork. OpenCode 1.18.30 injects the side-effect-free `StructuredOutput` response tool for the JSON-schema request, resolves the final model tool map through the merged agent-and-session rules where the last matching rule wins, and records its captured response on assistant `info.structured`. The fork's ordered session rule (wildcard deny, then exact `StructuredOutput` allow) keeps that host response tool while every operational tool stays denied. The installed 1.18.30 prompt path does not use `retryCount`, so Magic Compact does not send it. Magic Compact makes one `session.prompt` call per fork and adds no plugin-level provider or model retry or fallback; OpenCode may apply its runtime provider/transport retry policy or additional model steps required by structured-output processing. Treat the captured object as untrusted: require exactly one result, its target ordinal, exact marker echo, nonempty summaries, and exact visual coverage. Text parts are never parsed as a fallback. The response packing estimate includes the mandatory JSON envelope and all echoed protocol fields. Reject active nonce leakage. The first failure stops new batch admission, but every already-active worker drains through cleanup and contributes its sanitized failure in deterministic batch order. Then require exact once-only target ordinal coverage before framing any results for the mutation flow.
13. Any planning, batch, provider, throttling, validation, lifecycle, or cleanup failure discards every generated result; no successor is created and source and stats stay unchanged. Provider or validation failure directly awaits one abort attempt. Every created fork is directly deleted before its worker settles, and genuine abort or deletion errors join the sanitized failure. When several batches fail, the aggregate's message explains at most three distinct reasons and then names every partial fork (OpenCode 1) or temporary session (OpenCode 2) that could not be deleted, in batch order; those IDs are never part of the reason cap. The first failure stops new admission, but every concurrently started batch drains through its owned cleanup before command settlement. Native context overflow reports trim-first guidance; output exhaustion requires a model with more output capacity because every request covers a single turn. Magic Compact adds no plugin-level provider or model retry, adaptive repartitioning, model switching, or partial result acceptance; OpenCode may apply its own provider/transport retry policy or additional model steps required by structured-output processing.
14. Project the complete final canonical model-facing state with the same pure manifest projection used by the OpenCode hook, including v3 summaries, the model-facing boundary, planned pruning/omission notices, and declarative media placeholders. Tool parts kept by task-aware retention stay whole in this projection and receive no prune mutation. Keep a turn only when this exact projected count is strictly lower than its exact source count.
15. Recompute the eligible token base over selected profitable turns only and require at least 20% savings, subject to a small absolute floor and net of the fixed boundary overhead. A weak or empty result fails before a successor is created and records no stats.
16. Build the successor history by applying closed edits to a clone of the exact source records read in step 2: prepend each new v3 summary part to its turn's first assistant message, apply the planned part deletions, tool-part replacements, and message deletions by source ID, and prepend the post-compaction boundary to the next user message or, with no next turn, append it in a new synthetic user message. A media summary stores `metadata.magicCompact.mediaManifest` version `1`. Original file parts and URLs are not changed. No newly discovered part is swept.
17. Count the edited history with the same projection, check the 20% gate, then append the ignored stats notice reporting `Stored history (estimate)` before and after counts, the trimmed amount and percentage, the number of summarized request turns, and the whole turns `N` preserved. Appended notice messages inherit the latest user message's agent and model.
18. Create the successor (see Successor Sessions) with `operation: "compact"` and the new `compactionCount`, the planned omissions, and stats carrying net physical token pruning separately from current inline-image projection.
19. Require the successor's exact persisted history to count to the projected values, then show a success toast naming the summarized request turns, the successor session ID, the whole turns `N` preserved with the definition of a request turn, and retention feedback.

## Summary Contract

- Each batch captures one structured object on assistant `info.structured`. The fixed JSON schema requires one `turns` array whose `minItems` and `maxItems` are both 1, plus exact object keys and types; the prompt text states the same count. OpenCode 1.18.30 does not validate StructuredOutput arguments against this schema and sends function tools non-strict to `@ai-sdk/openai`, `@ai-sdk/azure`, and `@ai-sdk/amazon-bedrock/mantle` providers, so local checks remain the authority for count, identity, and coverage. Every turn object has exactly `ordinal`, `marker`, `summary`, and `visualDescriptions`; any other key, including a legacy `anchor`, fails as a shape error. Packing budgets the envelope/array punctuation and every mandatory field before estimated summary and description content. These target ordinals remain monotonic across batches and are distinct from global-index `sourceOrdinal` values.
- `ordinal` and `marker` must exactly match the bounded request index in order. Exact marker echo is required in the `marker` field. Response identity is the exact result count and order, the target ordinal, and the fresh nonce-bound marker. Response identity never requires the model to echo user text, so empty, duplicate, long, or model-transformed first lines cannot fail identity. Only the active exact generation nonce or marker token is forbidden inside `summary` and visual descriptions; useful source message, part, session, parent, and tool-call identifiers may remain when the model includes them. `summary` must be a nonempty string and must not contain the active exact nonce or marker token. The system prompt asks for readable continuation-focused Markdown preserving outcome, important process/decisions, verification, and unresolved/next work when present; the host does not impose a semantic status or evidence protocol.
- `visualDescriptions` is empty for a turn with no authoritative user or assistant inline images. Otherwise it has exactly one `{ordinal, description}` object per expected image in user-then-assistant encounter order, with a nonempty description that does not contain the active exact nonce or marker token. The host appends accepted descriptions under `Visual summary:`.
- Existing `metadata.magicCompact.summary === true` text parts are opaque persisted data regardless of version. Recompaction skips the entire containing turn message- and part-identically and never parses, migrates, rewrites, or upserts its summary ID. Trim preserves the summary part itself.
- New summaries use `metadata.magicCompact.summary === true` with `capsule === true`, `agentic === true`, and `version === 3`, as the first part of their turn's first assistant message. They are planned under `prt_-magic_capsule_v3_${messageID}` and persisted in the successor under a freshly minted part ID, so recompaction and trim identify summaries by metadata, never by ID. A media-aware summary additionally stores `mediaManifest: {version: 1, images: [{ordinal, mime, urlSha256}]}` for inline user then assistant images only. Historical v0/v1/v2 parts keep their bytes and IDs, but no legacy producer remains.

## Trim Flow

1. Parse `N` and the optional `--heuristic` flag; `N` defaults to `0`.
2. Show the view-only in-progress toast.
3. Build turns for the complete stored session, independent of compaction boundaries, and keep the loaded messages as the planned source snapshot.
4. Preserve the `N` most recent assistant turns.
5. Read the source at rest (see Successor Sessions). Unless `--heuristic` was given, run task-aware retention over the older turns. Any retention failure ends the command here, before a successor.
6. Apply the normal tool input and output trimming rules to clones of the older turns' completed tool parts, skipping parts kept by retention and planning, not allocating, omission IDs. Input trimming still applies to states already marked trimmed by an earlier run and changes only the input; output trimming applies only to unmarked states. Mark processed states with `state.metadata.magicCompact.trimmed === true`; kept parts are not marked.
7. If no tool state would change, show the no-op toast; no successor is created.
8. Replace each changed tool part in a clone of the source records, count the stored history before and after, and append an ignored notice reporting the `Stored history (estimate)` before/after counts, the trimmed amount and percentage, and the number of trimmed tool calls. Add one retention line matching terminal feedback, for example `Retention | Task-aware retention kept 4 of 9 evaluated tool call(s) whole (read 4).`
9. Create the successor with `operation: "trim"`, the source's unchanged `compactionCount`, the planned omissions, and the stored reduction, then require its exact persisted history to count to the projection before showing success.

`/magic-trim` never generates turn summaries, modifies ordinary user or assistant content, inserts a compaction boundary, or increments `compactionCount`. Its only model and TypeSafe requests are the task-aware retention summary and classifications; `--heuristic` makes none. Trim covers the complete stored history, including any prefix a native checkpoint hides from the model.

## Task-Aware Retention

- Candidates are completed tool parts in the command's eligible turns whose input or output the existing tool rules would change, determined by running those rules on a clone without allocating omission IDs. `/magic-compact` uses its summarized turns that carry no Magic summary; `/magic-trim` uses every turn outside the preserved `N` tail. With no candidates, no summary fork, model request, or TypeSafe request is made, and the key is not required.
- A missing `TYPESAFE_API_KEY` fails before any summary request.
- `MAGIC_COMPACT_KEEP_THRESHOLD_PERCENT` is optional: a plain decimal percent from 0 to 100 inclusive, with surrounding whitespace ignored (`70` is probability 0.70, `60.5` is 0.605, `0` and `100` are valid). Unset uses 0.60. An empty or whitespace-only value, a sign, `%`, an exponent, hex, `NaN`, `Infinity`, a value above 100 or any other form fails the command with a fixed message that names the variable and the range and never echoes the value, before any summary request, Jev request or successor write, whether or not candidates exist. Nothing is clamped or defaulted on error. The service that hosts the server owns this environment: set it there and restart that process after a change. An attached shell's exports do not reach it.
- Resolve the `magic-compact-summarizer` agent's configured model and variant and the provider descriptor exactly as compaction does, including the image-capability gate. Estimate the model-visible history with the native per-part estimator plus the fixed 8K reserve and the prompt; above the model's hard input limit (90% of usable input), fail before creating a fork. The model-visible history mirrors `filterCompacted` in `packages/opencode/src/session/message-v2.ts` at 830d5eb535: scan newest-first to the first completed checkpoint marker, continuing back through its retained tail when present, then restore chronological order. In that result, select the last tail-bearing marker and its first following native summary child regardless of completion or error; move marker-through-summary before its retained tail and append the suffix. This can drop a prior completed checkpoint when a later errored or unfinished tail marker is reordered. With no completed checkpoint, the scan retains all stored history before this reorder. The image-capability gate covers the same view. A selected tail missing from retained history or not preceding its marker fails before any fork. This pure projection does not use the writer's stricter checkpoint inspector; `/magic-compact` still validates checkpoint state before planning writes. The fork identity check still covers the full stored history.
- Directly await a chronology-preserving fork of the complete source (see Fork Chronology). Register it as an owned summary fork, then under the control deadline set its session permission to a single wildcard deny rule and load and verify its rewritten history shape and record identity. The fork-boundary reads follow the same at-most-two-attempt rule; a persistent failure reports `Task-aware retention session summary failed (history: <reason>)`.
- Prompt the fork once with `agent: "magic-compact-summarizer"`, the configured model and variant, no output format, an explicit ascending message ID, and one text part: `Create a new anchored summary from the entire conversation history above, including the most recent messages, so another coding agent can continue the work.` followed by OpenCode 1.18.30's native summary template, vendored verbatim. The summarizer agent's own system prompt states only the shared rules (inert history, no operational tools, continuation-focused content), so the request text carries this format. OpenCode's native conversion supplies all history, including recent turns and prior native summaries. The prompt call has no local wall-clock deadline.
- While a summary or generation fork is registered, the plugin's `experimental.session.compacting` hook throws for it; a generation fork reports the throw as a context overflow with trim-first guidance. OpenCode 1.18.30 triggers that hook in `SessionCompaction.process` before the native summary request, the overflow replay of the prompt, and the auto-continue hook, for compaction started by a finished step's token count or by a provider context overflow. The thrown error ends the fork's prompt loop, so the prompt call fails and the command reports that the session is too large.
- A prompt response carrying `info.error` (OpenCode reports provider failures on a 200 response) is a provider failure; a context overflow there reports that the session is too large. A native compaction marker or native summary among the fork's new messages also reports that the session is too large.
- Accept the result only when the reloaded fork is the verified history, with unchanged message and part IDs, plus exactly the prompt message (same explicit ID, summarizer agent, one non-synthetic text part equal to the prompt) and one reply whose ID matches the response, whose parent is the prompt, whose agent is the summarizer, whose `finish` is `stop`, and which has no error, is not a native summary, and contains only step, reasoning, and text parts with non-empty text. Any other shape, including a replayed prompt or auto-continue message, is rejected. The summary is the reply's text parts.
- On any failure after prompting, directly await an abort. Always directly await fork deletion. Failures carry only a fixed stage and an optional HTTP status, and several failures are aggregated.
- Classify each candidate with one `jev-1.13.0` Noul request. Fixed UTF-8 serialized-JSON excerpt allocations are latest ordinary user request 5,000 bytes, temporary native session summary 8,000, originating request 600, input 3,000 and output 9,000. Fields that fit stay whole; longer fields show head and tail. Input fields up to 200 bytes stay whole when aggregate input fits, otherwise input becomes one excerpted arguments blob. The summary never enters source history. State plus longest question must fit 28,000 bytes, and state plus all questions 56,000; these byte limits rely on empirical token headroom, not a documented tokenizer bound. Requests run at most four at a time, with a 30-second timeout and no retries; any failure stops admission, drains in-flight requests and discards every decision.
- Require a decision for every candidate. Keep the entire current part unchanged only when its probability is >= the keep threshold (0.60 by default, or the percent above); uncertainty trims. Judge likely reuse of concrete input or output independently, including duplicates, recoverable content, still-relevant task procedures and useful unchanged content in partly edited reads. Empty notices, bookkeeping and genuinely superseded or unrelated content do not qualify. No size cap, persistent pin or automatic restoration is added.
- Terminal feedback names the retention mode and the kept and evaluated counts, never tool content.
- Trim's notice and toast also show up to three kept tool names ordered by descending count with lexical ties, then the remaining kept-call count. Each label is capped at 24 characters with control/formatting characters and whitespace collapsed. The denominator is evaluated candidates, not all completed calls. Zero keeps, no candidates and heuristic non-evaluation are explicit; all-kept no-ops inject no notice and create no successor.

## Fork Chronology

The API's stored source message order is authoritative. In OpenCode 1.18.30, `Session.fork` copies records one at a time and mints each message and part ID from the host clock in milliseconds times 4096 plus a counter that resets whenever the millisecond value changes. Reads order parts by ID and messages by the row's immutable `time_created`, then ID, and a native fork inserts rows using copied JSON `info.time.created`. A host clock that steps backwards during the copy therefore reverses a valid history even when its source timestamps are monotonic, and an earlier message-info update that changed JSON time without its row key does the same to messages. Having run trim before is not itself a reason to reject a session.

- Summary and compaction generation forks use `forkSession`, and no fork is populated by the host's copy. Successors reuse the same history planning, replay, and exact persisted check on a newly created session. Before any host call, validate the planned history: every message belongs to the source session, message and part IDs are unique, parts belong to their message, creation times are safe non-negative integers, and every present assistant parent or compaction-tail reference resolves to a strictly preceding message. Dangling, forward, self, and empty references fail closed instead of being dropped or preserved under source IDs. Absent optional tails remain supported.
- Create the native fork cut exclusively before the first planned message (an empty history has no cut) and require its persisted history to be empty. Use the supported SDK `sync.replay` operation to append version-1 message and part events starting at sequence one, after the native session-created event at sequence zero. Mint message and part IDs locally from one clock reading plus an ordinal counter so they ascend in planned order, and rewrite preceding parent and checkpoint-tail links as native forking does. Each message is inserted with an ordered row key, then updated to restore its exact original JSON info. Parts, tool state, file URLs, provider metadata and Magic summary metadata stay intact. An empty history sends no replay, because the host requires a nonempty event list.
- Replay is directly awaited without a local deadline, retaining ownership of any server-side partial write. Reads use the control-operation deadline. After replay, require the reported session ID and the complete persisted reload to equal the locally rewritten history, including original JSON timestamps. Then reload the live source through the same session routing and require its normalized structural snapshot to match the planned history, rejecting appends, content changes, missing records, or reordered records. Source timestamp, token and cost churn is ignored only by that comparison and cannot bypass the exact persisted check. These checks precede permissions, prompts, and generation isolation. Sorting an in-memory array is insufficient.
- Population or verification failure directly awaits deletion of the partial fork, leaves the source unchanged and creates no successful stats increment. A failed cleanup reports the partial fork ID for manual deletion, and an aggregate of several failed batches names each such ID. A missing replay API or an incompatible host contract fails closed.

## Successor Sessions

Compaction and trim never write the source session or its subagent sessions. They write their result to a new root session through the public API and verify it before handing it over.

- **At rest.** The source must be a root session (no `parentID`). It must have no pending revert, no running native compaction (`time.compacting`), no unfinished assistant message, and no pending or running tool part. Every session in its subagent tree, found through `session.children`, must be idle or absent from `session.status`; `busy` or `retry` is active, and any other status type is treated as unsupported active state. No permission request or question in that tree may be pending. A background `task` (the experimental background subagent flag) returns at once with a running result whose metadata has `background: true` and the child `sessionId`, whether it was called with `background: true` or promoted from the foreground; each started job must be followed in the source by its delivery, a user message whose synthetic text part starts `<task id="<child>" state="completed">` or `state="error"`. A message to a job that is still running (`Background task updated`) starts nothing new. OpenCode 1.18.30 never delivers a cancelled job and lists no jobs publicly, so a cancelled background subagent leaves the session refused, naming the child; a background call without a child ID cannot be matched and is refused too. The command reads all of this before planning and again, completely, just before the successor is marked ready.
- **Unfinished history.** The unfinished-assistant and tool-part checks cover every stored message, not only recent turns, so a record the host never closed (an interrupted turn, or a background task that was running when its message was last written) refuses a session that is otherwise idle, even after later turns completed. An assistant message with an `error` and no completion time counts as closed. On OpenCode 1 the check runs after the status, permission and question checks, so a session that is actually busy or waiting reports that instead. The refusal is a `SourceNotAtRestError` built in `src/policy/successor.ts` for both hosts. The sentence leads with the outcome and the next step: the stored history has an unfinished record that blocks even an idle session; if work may still be running, wait and retry; otherwise continue without the command or in another session; for `/magic-trim`, `--heuristic` does not skip the check; the session was left unchanged. A trailing `Record:` line carries the references, so the sentence reads without them: the first record in stored order by message ID and, when that message holds an unfinished tool call, the tool name, call ID and state, with the other messages counted instead of listed (`Record: assistant message msg_x; no completion time or error; running bash call call_y and 1 more call; plus 2 more messages.`). Labels are cut to `[A-Za-z0-9_.:-]` (anything else becomes `?`) and capped at 64 characters (24 for a tool name, 16 for a state); no tool input or output, prompt, reasoning, error body or other metadata is rendered. With every label at its cap the text stays under 600 characters on OpenCode 1 and under 700 for the OpenCode 2 form that also names a subagent session, counts of up to three digits included, so the failure toast (cut at 700) shows all of it. When the same failure also keeps a successor candidate (the source changed while the successor was prepared), the candidate's ID, that this run did not mark it ready and what to do about it come before the `Record:` line, which is the part the toast cuts. The text does not claim that work is running or abandoned, does not promise that waiting, restarting or native compaction clears a stale record, and never suggests editing the database.
- **Drift.** The second read must match the first on the normalized message history (the same normalization as fork verification: timing, token and cost churn are ignored) and on the continuation state the successor copies: directory, workspace, title, agent, model, permission rules, and metadata. A difference discards the unready successor. This detects change; OpenCode 1.18.30 offers no compare-and-swap, so it is not a lock. Within one plugin process, a second compact or trim command for a source that already has one running is refused.
- **Creation.** `session.create` receives the source's directory, workspace, agent, model (with variant), permission rules, and metadata, plus a `magicCompact` metadata entry `{compactionCount, successorOf, operation, createdAt, ready: false}` and the title `<source title> (preparing)`. No `parentID` is sent, so the successor is a root session. The source's own `magicCompact` metadata is replaced by the new entry.
- **History.** The edited history is planned and replayed exactly as in Fork Chronology, onto the new session whose history must be empty first. The persisted reload must equal the planned history, then the source cache is copied with every existing omission ID and byte unchanged, the planned omissions are committed, and stats are written. Imported assistant message IDs are recorded as processed, so replayed history never adds cached-read savings; new responses in the successor do.
- **Ready.** After the source recheck, a second exact reload of the successor and a fresh read of its session record, one `session.update` restores the source title and sets `ready: true`. The candidate's record must match what the command wrote at creation and again just before the update: parent (none), directory, workspace, preparing title, agent, model and variant, permission rules, metadata with the lineage entry, no revert, archive or running compaction, and the project, path and share the host assigned at creation. The update's returned record must show the same fields with the source title and `ready: true`. This is a fresh check, not a lock: OpenCode 1.18.30 offers no compare-and-swap. The plugin's TUI companion, which the OpenCode 1 TUI loads only when the package is listed in `tui.json` `plugin`, listens for `session.updated`. Every TUI with the plugin whose current route is the source session opens the ready successor, once per successor, whichever client ran the command (another terminal or a headless client); two TUIs on the source both move. A TUI on any other route is left alone, and the source stays available.
- **Failure before ready.** The candidate is deleted, with its caches and stats, only when fresh reads show nothing but what the command wrote: the record above, a prefix of the planned history (a partly applied replay may leave a message's ordering seed, which is the planned record with its creation time set to its index, or a prefix of its parts), no child session, an idle or absent `session.status` read on the candidate's own directory and workspace, and no pending permission request or question. A candidate another writer changed, one with child sessions or work, or one that cannot be read, is kept and its ID is named in the error. Once the ready update has been sent, a failure keeps the successor and names it, because the host may already have applied the update.
- **Failure reports.** A successor failure's message is fixed text plus, when relevant, the source or kept candidate ID. Its `details` hold only the stage (`plan`, `create`, `import`, `verify`, `instructions`, `cache`, `stats`, `recheck` or `ready`), a fixed verification or replay category raised by the plugin itself, an HTTP status from 100 to 599, a known Node system error code (such as `ENOSPC` or `EISDIR`), the source ID and the kept candidate's ID. The host's error is never attached as a cause, and its name, message, body, path or other code is never repeated; only the plugin's own at-rest and drift refusals keep their fixed messages. Fixed texts name the source as the original session. A kept candidate is named as kept and the text says that this run did not mark it ready, because the candidate's record is kept exactly when it could not be confirmed as unmodified and another writer may have set `ready`. On OpenCode 1 the `status` is the HTTP status of a refused `session.create` or ready `session.update` response, when the host sent one; nothing else of the response is kept. On OpenCode 2 a status is kept only when the error has its own `status` or `response.status`; the client's `ClientError` for an unexpected HTTP status keeps it in `cause.status`, which is not read, so a V2 failure usually shows no HTTP status. Failure feedback shows the message with the `Details:` line built from `details`. An at-rest refusal carried through a successor failure keeps its `Record:` line last, after any kept-candidate text.
- **Original.** The source keeps its messages, parts, title, metadata, omission cache, and stats byte-for-byte. The original native subagent sessions stay attached to the source; successors reference their captured reports through the copied history and omission cache, and the current session authorizes retrieval.

## OpenCode 2

OpenCode 2 runs the same commands, tool, policy and successor model as OpenCode 1 through its own adapter in `src/host-v2.ts` and `src/v2/`. These are the differences.

### Setup and connection

- Configure the plugin under `plugins` and the summarizer under `agents`: `"agents": {"magic-compact-summarizer": {"model": "provider/model#variant"}}`. OpenCode 2 plugins cannot add agents, so the agent exists only when the operator defines it. `setup` updates that entry's description, mode (`subagent`), hidden flag, system prompt and permission rules (deny all) and keeps the operator's model and variant. Commands read the agent and the model list at the source session's own directory, so a project's `agents` setting applies; the server's default location is not consulted for them. A missing agent or model fails the command with setup guidance; neither the source model nor native compaction is a fallback.
- OpenCode 2 gives plugins no transfer, history or instruction-entry APIs, so compact and trim use the public `@opencode/client` 2.0.28 over this server's HTTP API. The endpoint is either the registered service from `Service.discover()` (never `Service.ensure()`, which could start one), or the plugin's `serverUrl` option with basic auth from `OPENCODE_SERVER_PASSWORD` and `OPENCODE_SERVER_USERNAME` (default `opencode`). An endpoint qualifies only when `server.info()` reports this plugin's own process ID and its `session.get` of the source returns the same ID, project, creation time and location as the in-process plugin context. Otherwise the command fails with startup guidance before any read or write: run OpenCode through its registered background service (the default for the OpenCode 2 TUI and `opencode run`), or set `serverUrl` to this server's own listener. A private `opencode run --standalone` server is not supported. A standalone `opencode serve` that also finds another process's registered service refuses. No port is guessed.
- `/magic-stats` reads only plugin storage and the in-process session, so it needs no endpoint.

### Commands and feedback

- Command names, arguments and validation are the same. Each handler throws its result message, as on OpenCode 1. OpenCode 2 returns a thrown command error's message to the client as a `CommandExecutionError`, so a headless client receives the success message with the successor ID, the no-op message, the stats summary or the failure. A compact or trim failure uses the OpenCode 1 failure text: a plugin error whose message is already that text is rethrown unchanged, and anything else is thrown as a new error carrying the text, with the original as its `cause`.
- OpenCode 2 has no server toast API and no ignored messages. Compact and trim show no progress toast and append no stats notice to the successor; the outcome text (the notice's `Stored history (estimate)`, change and retention lines) is stored in the successor's `metadata.magicCompact.outcome` and included in the thrown success message. `/magic-stats` returns its summary as the thrown message instead of injecting a notice.
- The TUI companion listens for `session.metadata.updated`. When a successor's lineage turns `ready`, every TUI with the plugin whose current route is that successor's source session navigates there once and shows the outcome as a toast, whichever client ran the command, headless clients included. A TUI showing anything else is left alone, and the source stays available.

### Source at rest

The source must be a root session (a forked root session qualifies) with no pending revert. Its complete history is read with paginated `message.list` (ascending, then by cursor) and must equal `session.export({sanitize: false})`, so a page boundary or host filter that loses records fails. The command refuses when, anywhere in the source's subagent tree (found through `session.list({parentID})`), a session is in `session.active()` (reported as running), an assistant message is unfinished or holds a streaming or running tool call, a compaction or shell record is running (reported with the unfinished-record message described under Successor Sessions, shared with OpenCode 1, which also names the subagent session when the record is in one), the inbox holds a queued message, a permission request or form is pending, or `shell.list` shows a running shell whose `metadata.sessionID` is in the tree. A completed `shell` or `subagent` call made with `background: true`, or one whose result metadata has `status: "running"` (a foreground call the user detached with `session.background` keeps its original input), must be matched by its delivered notification (a synthetic message whose metadata has `source: "shell"` and the call's `shellID`, or `source: "subagent"` and the call's child `sessionID`, with state `completed`, `cancelled` or `error`); a background call that cannot be linked counts as undelivered. A notification does not prove the job has stopped (a cancellation notice is written when the cancel is accepted), so every such job must also be absent from `session.active()` (subagent) or not running in `shell.list` (shell). The drift check compares the full history and the continuation state: title, agent, model, permission rules, metadata, location, subpath, project and active instruction entries.

### Successors

- The successor is created with one `session.import`: the source's session info with a fresh descending session ID, the source title plus ` (preparing)`, the source metadata plus the lineage entry, and no parent, fork or revert; and the edited history under fresh ascending message IDs minted from one clock reading. Import keeps array order and requires message IDs that are unique across the database. Fork lineage is not copied; `metadata.magicCompact.successorOf` names the source. The lineage entry is `{compactionCount, successorOf, operation, createdAt, ready, outcome}`.
- The imported session and history must read back exactly as planned: no parent, fork, revert or archive time, the preparing title, and the source's agent, model, permission rules, location, subpath, project and metadata with the lineage entry. Then the source's active instruction entries are copied with `instructions.entry.put` and must list back equal. Host-generated instruction-change notices (`system` messages whose `metadata.notice` is `"instructions"`) are not copied: they describe deltas against the source's instruction history, and the successor starts from a fresh baseline holding the current entries. User messages and every other record are copied unchanged.
- After caches and stats are written and the source is rechecked, the record, history and instruction entries are read and compared again, one `session.update` restores the title and sets `ready: true`, and all three are read back once more with the ready title and lineage. Cleanup follows OpenCode 1: an unready candidate is removed (with its cache and stats) only when fresh reads show the record it imported, the planned history or none, only instruction entries copied from the source, no child session (`session.remove` also removes children), no `session.active()` entry, and an empty inbox, permission list and form list; otherwise it is kept and named.
- Omission caches and stats live under `${XDG_DATA_HOME:-~/.local/share}/opencode/storage/magic-compact/v2/`. OpenCode 1 and OpenCode 2 sessions never share a cache or stats file and nothing is migrated between them. Planned omission IDs take their diagnostic prefix from the native session ID. `read_omitted_content` is registered as a direct tool (`codemode: false`) and reads only the current session's OpenCode 2 cache. Stats add savings once per `session.step.ended` assistant message.

### Tool calls

- A tool call is identified by its message ID, its position in the message's content and its call ID. OpenCode 2's tool names map onto the rule categories (`write`, `edit`, `patch`, `shell`, `subagent`, `read`, `question`, `skill`); every other name, including code mode's aggregated `execute`, follows the default rule as one call.
- The rules judge a completed call's input and its text output: the text content items joined with a blank line. A replaced output takes the place of the first text item and drops the other text items, and file items keep their positions. Input references live in the input and never add a content item. A subagent call's child session is `metadata.sessionID`, read only when it is a native `ses_` ID. Processed calls get `state.metadata.magicCompact.trimmed`. Task-aware retention classifies the same text rendering; it is never persisted.

### Compaction

- Turns are planned after the newest completed native `compaction` record, whose summary and recent context make earlier records invisible to the model; those records are copied unchanged. A Magic boundary is a synthetic message with `metadata.magicCompact.boundary`; the latest one after that floor starts the eligible range, `N` preserves the most recent complete turns, and a turn whose assistant message carries `metadata.magicCompact.summary` is opaque.
- Each target turn is summarized in its own owned temporary session imported under fresh IDs: the target's records, at most the one complete preceding turn within the halo limit, and a synthetic marker message before the target's first user message. Later turns never enter the request; they reach the model only as user anchors in the global map, and the successor keeps them unchanged. The session uses the summarizer agent and model and the permission rules deny-all then allow `StructuredOutput`. The plugin registers `StructuredOutput` as a direct tool with the shared response schema; its executor acknowledges only when the call's `sessionID` is a per-turn generation session this process owns and otherwise throws. The `context` hook advertises it only to such a session; the `context`, `generate` and `compaction` hooks remove it from every other session and request kind, retention sessions included, and a `title` request has no tools. The one shared protocol text (`GENERATION_PROTOCOL`) says a marker is either added to the turn's first user message (OpenCode 1) or sent as a separate synthetic message directly before it (this layout), and bounds the target from its marker to the end of the retained history; anything before the marker is preceding context for orientation only.
- The command prompts once and waits. The `context` hook lets an open owned session make one provider request and throws a per-process stop on the next and on every request once the session is closed, so after the response-tool call the host records a failed idle whose error is that stop. The `compaction` hook throws a different per-process token for owned sessions, and a `title` hook result skips title generation. A response is accepted only as the copied history, the prompt, one summarizer reply whose only tool call is one completed `StructuredOutput` call, and the host's record of the owned stop. OpenCode 2 repairs and strips tool arguments before its executor runs but persists the model's raw input, so validation reads the persisted `state.input` with the shared strict checks. A text reply, a rejected call, a duplicate call, a provider error or anything else fails the command; a blocked native compaction or a context-overflow error reports trim-first guidance. Every temporary session is removed. At most five run at once; the first failure stops new requests and every failure is reported in target order.
- An owned session's import and removal are awaited until they settle, with no local deadline, because an abandoned request could still create or keep the session later; only reads use the control deadline. `session.remove` interrupts and waits for the session before removing it. Before removing a session, the command closes it: from then on the `context` hook stops every provider request there, including a session the host created from an import that then failed, or whose history failed verification before any prompt. The session stays registered and closed until a removal succeeds. When the removal fails or its result is unknown, the command fails (generation names the temporary session, and an aggregate of several failed turns names every one) and the registration stays for the life of the process, so the `context` and `compaction` hooks keep refusing any further provider request or native compaction there. A removal that reports no such session keeps the registration too, since a failed import may still be applied late. Nothing is retried.
- A profitable turn keeps its user messages exactly. Its first assistant message carries the summary as its first content item and `metadata.magicCompact = {summary, capsule, agentic, version: 3}` (plus a media manifest when the turn has inline user images). Assistant text and reasoning are dropped, tool calls stay with the tool rules applied except retention keeps, and empty assistant messages are dropped. The boundary is inserted before the next turn's first user message, or appended.
- Host records in a summarized turn follow the OpenCode 1 rule for injected user text (`keepsHostInjectedText` in `src/policy/host-text.ts`): text that carries the conversation forward stays and transient host reporting goes. Shell and subagent notifications (synthetic messages whose metadata has `source: "shell"` or `"subagent"`) carry results and keep their exact bytes. The restart notice (metadata exactly `{notice: "restart"}`) is dropped. A synthetic message without metadata is how OpenCode 2 stores a migrated OpenCode 1 synthetic part (several parts joined by blank lines), a plan-mode reminder or the "moved to the background" notice; it is dropped unless its whole text or any blank-line-separated part is a user-run tool notice, a `<task ` result, a working-directory change or a user comment. The plan agent re-adds its reminder while it is active. Skills, user shell runs, location, model and agent switches, system notices and synthetic messages with any other metadata carry state and stay. Recent preserved turns, opaque summary turns and records before the newest completed native compaction are never edited.
- Inline user images are the files OpenCode sends as image media (`session/runner/to-llm-message.ts` in 2.0.28): MIME `image/png`, `image/jpeg`, `image/gif` or `image/webp`, and, once a message holds two or more mentioned inline images, a repeat with the same MIME, name, description, mention text and data only once. Other image types never reach the model and are not counted. Each target counts and describes these images, and its summary binds them in a manifest of send ordinal, exact MIME and the SHA-256 of the exact stored base64 data (`{version: 1, images: [{ordinal, mime, dataSha256}]}`). The stored data is never changed; before a summarizer is asked to describe an image, its data must be canonical, non-empty base64. Tool file content is native tool media: it stays in place and never enters a manifest.
- The `context`, `compaction`, `generate` and `title` hooks project every model request built from a session's history, owned sessions included (`src/v2/media.ts`). When a request message carries a manifest, the hook reads the session's native history with the in-process `session.context` and pairs request messages with records by the native message ID OpenCode keeps on converted messages. `session.context` starts at the newest completed compaction, but the runner picks the history a request replays by the model's provider route (`session/history.ts`): a provider checkpoint (`providerContext`) replays only on the route that wrote it, so after a switch to another model the request replays older records, and on the checkpoint's own route the checkpoint replays its retained copies of recent user messages under the IDs those messages had when the checkpoint was written. A successor and a native fork (`session/projector.ts`) copy the checkpoint unchanged under fresh record IDs, so a copy can arrive under an ID no record holds. Such an image-carrying copy is bound to its source by the checkpoint's order of copies, never by its images. Every user copy a completed checkpoint retains, with or without images, is taken as the copy of a distinct user record before that checkpoint, in the same order, with the same non-media identity: its text parts as OpenCode sends them (skills' text optional, because the checkpoint's retained window drops skills; attachment text such as `Attached file:` locations included) and its metadata (forwarded `agents` included). The text OpenCode puts in a copy in place of media it does not send (the error text for an input the model cannot take, or the removal notice for an image past the 25 MiB request image limit, both from `session/model-request.ts`) counts as media on both sides, so such a copy still matches its record; this can only widen the records a copy may stand for. A copy whose ID still names a record is that record's. A copy may stand for every record that some such order-preserving assignment of the whole checkpoint gives it, found from the earliest and the latest assignment in O(copies x records) without enumerating assignments; a checkpoint with no assignment fails the request. For every record it may stand for, the copy must carry exactly that record's sent images by MIME, data hash and order, and all of them must be projected identically, or the request fails before anything is sent, including when nothing would be projected. So a copy changed to another message's image, swapped images, or one copy that may stand for a summarized or an unsummarized message with the same text fails, and so does a reminted copy that OpenCode left with only some of its record's images, while identical messages projected the same way are projected. Strict order between the checkpoint's copies and their sources is OpenCode 2.0.28's trigger behaviour (`recentUserMessages` keeps a converted suffix of user messages); an endpoint checkpoint's replacement has no documented order, so a replacement that does not fit this order fails closed. Stored records, the checkpoint's provider-owned `providerContext` and user messages are never rewritten and no ID map is stored, because a native fork would remint the IDs again. When a request message carrying images is not in `session.context`, the hook reads the complete history over the server's HTTP API with the verified connection the commands use, kept for later reads and dropped on failure; if that read fails, the request is refused rather than sent with summarized images inline. A request that carries such images but no manifest (on the checkpoint's route, the retained copies may be the only trace of a summarized turn) is checked only in a session whose metadata holds Magic Compact lineage (`metadata.magicCompact`) or that this process owns, the only sessions that hold capsules; any other session's requests read nothing. An owned session copies its source under cleared metadata, so only the in-memory registry qualifies it, never anything a session stores. Every capsule is checked on its own over the records read, whatever compaction lies between it and the end of the history, and only turns the request represents are checked and projected. A summarized turn must still hold exactly the images its manifest binds, in order, with the same MIME and hash, and every request occurrence of one of its user messages, repeated checkpoint copies included, must carry exactly those images as base64 media; a changed, added, missing or reordered image, or a malformed manifest, fails the request before it is sent. Each covered image is replaced by the shared declarative placeholder text only when the placeholder's canonical token count is strictly smaller than the stored data's, so a small image stays inline. The replaced message is rebuilt with its own constructor; stored records, successors and exports keep the original data. A request without a manifest is unchanged and reads nothing.
- The same projection decides per-turn profitability, the savings gate, token verification and stats: a turn is kept only when its projected count is strictly lower, physical pruning (`tokensPruned`) excludes projection, and the successor's stats record the current projected image tokens (`mediaTokensProjected`), which `/magic-trim` keeps for existing summaries. These counts cover every capsule in the whole stored history, including turns behind a native compaction, as on OpenCode 1. They are canonical stored-history estimates, not a claim about each request: a request that replays only a native summary or an opaque provider checkpoint sends none of those images, and a provider checkpoint's own content is outside the plugin's view. File payloads (user file data and tool file URIs) are tokenized in 1,024-character segments, and a large payload once per process by its SHA-256, because the tokenizer is quadratic on a long uniform run; projection decides placeholder size from the payload's byte length when that alone proves it larger.
- Before any temporary session, each generation request is checked against what OpenCode 2.0.28 does to request media after the plugin's hooks (`session/model-request.ts`): an image the model cannot take, or a GIF on xAI, becomes an error text, and more than 25 MiB of image data (unprojected user image data plus tool image URIs) drops the oldest images. Any unprojected image in a request for a summarizer without image input or one xAI does not accept fails the command with the image-model guidance, and a target turn whose manifest binds images fails when its request carries more than 25 MiB of image data. A model-written description is never taken as proof that the summarizer saw an image or described it accurately (see `docs/Core.md`).
- The temporary retention summary uses the same owned controls in a deny-all copy of the source and accepts only the prompt, one finished summarizer text reply and a successful idle. Before that copy is created, the history OpenCode will send for it, the summary prompt and the fixed 8K host reserve must fit the summarizer's hard input limit (90% of usable input), and a history that still shows an unprojected image needs an image-capable summarizer; otherwise the command fails with no session and no provider request. That history starts at the newest completed plain compaction. A provider checkpoint (`providerContext`) replays only on a compatible route the plugin cannot see, so the estimate counts from the newest plain compaction and includes later checkpoints, which can only overcount. An unlisted summarizer model fails the command and a missing output limit uses the shared 32K fallback. `/magic-compact` resolves the summarizer model and descriptor once for the retention summary and every generation; `/magic-trim` resolves them only when it needs a summary.

## Turn Selection

- Messages are processed oldest-first.
- A turn is one or more adjacent user messages plus all following assistant messages before the next user group.
- Consecutive user/no-reply messages stay in the same turn.
- Boundary detection runs before ignoring a trailing assistantless turn.
- A trailing user-only turn does not count against `N`.
- Only turns with assistant messages are summarized.
- A valid completed native checkpoint is a user message with exactly one `compaction` part and exactly one native summary assistant child whose `parentID` is the marker ID, `summary` is `true`, `finish` is truthy, and `error` is absent.
- Every marker is checked against all native summary children. Ambiguous, incomplete, errored, nested, crossed, orphaned, dangling, or forward checkpoint artifacts fail closed, except an older complete artifact set wholly frozen by a later valid checkpoint.
- The newest valid checkpoint owns an immutable prefix through its summary assistant. Turn construction starts strictly after that summary.
- Every completed checkpoint candidate's `tail_start_id`, when present, resolves to a durable message strictly before its marker. The retained tail, marker, summary message, summary text, and summary parts remain untouched.
- Native checkpoint marker/summary turns are never admitted as the preceding halo, so a retained halo cannot carry a `tail_start_id` into deleted history.
- Magic boundaries before the native checkpoint are ignored. The latest Magic boundary in the eligible suffix controls recompaction.
- `N` preserves the most recent completed request turns in the eligible suffix only. The plan exposes the actual preserved count as `preservedTurnCount`, which is smaller than `N` when `N` exceeds the eligible turns and counts only turns after the latest Magic boundary.
- If the suffix has no eligible turns after applying `N`, no successor, generation fork, boundary, or stats are created.
- The generation global index spans every complete turn in this effective suffix, including the complete retained `N` tail and opaque Magic-summary turns, while excluding a trailing assistantless active turn.
- `/magic-trim` selection spans the complete session and ignores compaction boundaries.

## Recompaction

- Any turn containing a previous Magic summary part is preserved as-is, including v0/v1/v2 and current v3 envelopes, even if a historical boundary is absent.
- Persisted media-aware v2 turns remain opaque. Their manifests and current v3 manifests still project independently; summaries without manifests receive no retroactive repair.
- Recompaction recognizes summaries by metadata, not by summary text or one ID namespace.
- Recompaction starts at the latest boundary marker, unless a later native checkpoint advances the immutable floor.
- Turns rejected by the per-turn profitability gate are never summarized or pruned by that run and fall before the new boundary.

## Media Request Projection

- The server plugin registers `experimental.chat.messages.transform`. OpenCode invokes it with the retained messages array and later converts that same array, so the hook computes `projectManifestCoveredMedia` and atomically replaces the retained array contents via `splice`. Projected messages and parts are clones; a failure leaves the retained array byte-identical.
- Projection considers persisted v2 and current v3 summary envelopes with `mediaManifest`. A turn without that manifest is unchanged.
- A v3 manifest-bearing turn must have exactly the same ordered set of inline user then assistant `data:` `image/*` file parts. Persisted v2 manifests remain user-only. Manifest version/shape, sequential encounter ordinals, exact MIME values, and SHA-256 of each exact URL must all match. Persisted v2 entries still require valid unique `partId` compatibility fields, but projection does not compare those ephemeral IDs.
- Every exact match is replaced by one synthetic declarative text placeholder with the same record identifiers only when the placeholder's canonical token count is strictly smaller than the original file URL token contribution; otherwise the exact file part stays inline and model-facing. Any missing, added, duplicate, reordered, MIME-changed, URL-changed, or malformed entry throws before model conversion; the hook never silently falls back to changed media. Because every replacement strictly reduces canonical tokens, projected media token counts are non-negative by construction.
- This same function drives per-turn profitability, complete post-compaction projection, final token verification, and model-facing stats. It never rewrites SQLite, stored sessions, API records, or exports.

## Omission Cache

- Location: `${XDG_DATA_HOME:-~/.local/share}/opencode/storage/magic-compact/{sessionId}.json`.
- Cache format version is `2`.
- Newly allocated IDs are `<last-12-session-chars>:omitted-<22-char-base64url-token>`, where the token contains 128 random bits. The prefix is diagnostic only and never routes a lookup.
- Each v2 entry stores content and a SHA-256 binding over its qualified ID and exact JavaScript UTF-16LE code units. Lone surrogates are preserved and Unicode is not normalized.
- Valid v1 bare entries are preserved under `legacy.entries` during migration and successor copying, but no new bare ID is allocated and bare legacy bytes are never returned.
- An absent source cache materializes as an empty v2 cache when copied to a successor. Planned omission IDs carry the source session's diagnostic prefix because they are planned before the successor exists. Malformed, schema-invalid, or integrity-invalid caches fail loudly and are not reset.
- Cache writes use atomic temporary-file replacement. In-process mutations for one session are serialized; distinct sessions remain independent.

## Omission Retrieval

- `read_omitted_content` accepts one `contentId` and receives `context.sessionID` from OpenCode.
- Retrieval reads only the current session cache and never routes by the diagnostic ID prefix.
- Retrieval returns the whole exact historical snapshot from the cache, not a new assignment or proof of current file state. The plugin returns the full string. OpenCode's plugin tool wrapper may truncate a large result (default limits 2000 lines or 50 KiB) and provide a reference to the full saved output; see `fromPlugin` in [registry.ts](https://github.com/anomalyco/opencode/blob/830d5eb535/packages/opencode/src/tool/registry.ts) and [truncate.ts](https://github.com/anomalyco/opencode/blob/830d5eb535/packages/opencode/src/tool/truncate.ts). The tool description, shared by both hosts, explains the references once; it says that OpenCode may truncate a large result, to retrieve an omitted task prompt before reuse and to reread files for current contents. A Content ID works only in the session whose cache holds it, including entries copied into a successor; an ID copied into an unrelated session, such as a subagent's, is refused.
- Missing authorization, no exact entry, invalid integrity, malformed cache, and bare legacy IDs return explicit unavailable/integrity diagnostics and never guessed bytes.

## Stats

- Stats are stored under `${XDG_DATA_HOME:-~/.local/share}/opencode/storage/magic-compact/stats/{sessionId}.json`.
- Stats cache format version is `1`; media fields remain optional for existing files.
- Stats track root/source session IDs, net physically pruned canonical tokens, physical cached reads, projected inline-image tokens, projected-media cached reads, and processed assistant message IDs.
- A successor's stats start from the source's totals (`rootSessionId`, cumulative pruned tokens and cached-read savings), set `sourceSessionId` to the source, add the command's exact canonical reduction, and record the current projected inline-image tokens. The source's stats file is not changed. Assistant completion events in a session add current physical and projected-media savings once per assistant message. Stats describe the working conversation, not disk use: the original session still stores its full history.
- `/magic-stats` injects an ignored stats notice, or a no-stats message if no stats exist.
- The `/magic-stats` notice distinguishes canonical model-facing estimates from provider context usage and reports cumulative stored savings. Compact and trim notices report the canonical `Stored history (estimate)` before/after counts of the whole stored session (including any prefix a native checkpoint hides from the model), the trimmed amount and percentage, and the operation kind. OpenCode's context meter is a provider usage snapshot; in a successor it can show the copied last response's usage until a later assistant response refreshes it. Magic Compact never fabricates provider counts or mutates provider metadata.

## Pruning

- Pruning applies only to summarized turns and is planned against the source records before the successor exists.
- User file/image parts and assistant inline images covered by an accepted v3 manifest are never prune targets or omission entries. Exact persisted URLs remain authoritative.
- The selection is rejected if it contains a native `compaction` part or native summary assistant.
- Projection plans every delete and tool replacement by explicit source ID, and the same plan drives both the profitability projection and the successor history. Newly discovered parts are never swept.
- Synthetic user text is deleted unless it is a preserved OpenCode wrapper or reminder.
- Summarized assistant messages keep summary parts, tool parts, and v3 manifest-covered inline image files. Other assistant parts are deleted; empty assistant messages are deleted.
- Only completed tool parts are pruned. Pending, running, and error states remain.
- `/magic-trim` applies only tool rules and marks processed states. Marked states are not output-trimmed again, but idempotent input rules still apply to them.
- Tool parts kept by task-aware retention are neither updated nor marked by either command.

## Tool Rules

- Every input omission replaces the field with its own reference, so the Content ID sits where the omitted content was. The model-facing output is unchanged by an input omission.
- `write`: omit large `input.content` and cache it; the field becomes `[Omitted; Content ID: <id>]`.
- `edit`: omit large `oldString` and `newString` together and cache once as `oldString`, a newline and `newString`; the fields become `[Omitted with newString; Content ID: <id>]` and `[Omitted with oldString; Content ID: <id>]`.
- `apply_patch`: omit large `input.patchText` and cache it, with the `write` reference.
- `bash`: cache a command over 1024 characters whole; keep its first 512 characters followed by `[Command truncated; Content ID: <id>]`.
- `read`: always cache and omit output as `[Historical read result omitted (<bytes> bytes); Content ID: <id>]`.
- `task`: omit and cache large `input.prompt` once as `[Historical task prompt omitted; Content ID: <id>. Retrieve before reuse.]`, a placeholder that is not a new assignment. Cache and omit output only above the higher task threshold, under a separate ID, as `[Task output omitted (<bytes> bytes); child session: <id>; Content ID: <id>]`. The child clause appears only when the host reported a native `ses_` child session ID in its own task metadata (`sessionId` on OpenCode 1, `sessionID` on OpenCode 2); other metadata, report text and requested resume IDs are never used.
- `todowrite`: preserve input and replace output with a success message, no cache.
- `question`: preserve input and output.
- `skill`: preserve input and replace output with a reload hint, no cache.
- Other completed tool outputs are cached and omitted above the default threshold as `[Output omitted (<bytes> bytes); Content ID: <id>]`.
- Input rules are idempotent on their own result and still apply to states marked trimmed by an earlier run; output rules are skipped on marked states.
- Histories trimmed earlier keep their `<tool-input-omission-notice>` and `<tool-output-omission-notice>` blocks, bare `[Omitted]` inputs and long task placeholders unchanged; no migration, reallocation or reformatting occurs on repeat trimming.

## Error Handling

- Any summarizer configuration, fork lifecycle, request, response contract, media manifest, SDK, cache, stats, token count, projection, or pruning failure aborts the attempt.
- Generation errors expose only fixed lifecycle stage/kind text, source session ID, validation category, and range-validated HTTP status. Validation categories distinguish missing structured output, invalid envelope, turn count mismatch, invalid turn shape/identity, invalid summary, invalid visual coverage, and nonce leakage; a turn count mismatch reports only its expected and received integers, and a turn shape/identity failure reports only the first failed check (`shape`, `ordinal`, or `marker`) and its target ordinal. Active-batch failures are ordered by batch in a sanitized aggregate. A failed fork-boundary history initialization adds one fixed reason to the generation error (`Compaction generation fork history verification failed|timed out (<reason>)`), so a read timeout is no longer reported as a shape mismatch; the reasons are `history read timed out`, `history read failed`, `history read returned invalid data`, `fork was not empty`, `history replay failed`, `replayed fork did not match the plan`, `source history was invalid`, `source history changed`, or `host returned an invalid fork`. Raw provider/control/model errors, bodies, prompts, fork history, model output, and aggregate causes are not retained in the surfaced graph.
- Native context overflow reports trim-first guidance. A configured model input budget too small to fit the fixed 8K non-explicit host reserve, or the reserve plus the complete explicit request and mandatory global index, fails before any fork with trim-first/model-capacity guidance. Exact real-nonce prompt or response-protocol variance beyond its conservative record also fails before fork creation. Output exhaustion requires more model output capacity because every request covers a single turn. When structured output is absent, truncation signaled by `finish` or an output-length error reports capacity guidance; a missing structured response without truncation reports a fixed message that the model finished without submitting its `StructuredOutput` response. A captured structured object still passes local validation when `finish` reports truncation. Other provider errors retain precedence, and a genuine non-`StructuredOutput` provider error always rejects the response. Magic Compact adds no plugin-level provider or model retry, adaptive repartitioning, alternate-model fallback, or partial mutation. OpenCode may apply provider/transport retries or additional model steps required by structured-output processing.
- Task-aware retention failures (missing key, summary budget or lifecycle, response shape, classification, or a missing decision) fail before a successor is created, discard every decision, and suggest `/magic-trim --heuristic`.
- Native checkpoint errors fail before generation.
- At-rest refusals, including a pending revert, name the active state and leave the source unchanged. Users restore a pending revert with `/redo` or let a normal OpenCode prompt commit the discard before retrying.
- Successor failures follow Successor Sessions: an unready, unmodified candidate is deleted; a modified, unreadable, or possibly ready candidate is kept and named. No failure writes the source or its stats.
- In-progress, no-op, success, and failure toasts use the shared best-effort control-operation deadline helper. A late-settling timed-out progress request reasserts the latest terminal toast without delaying command settlement. Toast timeout or failure cannot change the command result or replace the root error. A progress request applied remotely after its client promise rejected remains an undetectable host-side race.
- The command hook throws so OpenCode does not continue sending the slash command to the LLM.
