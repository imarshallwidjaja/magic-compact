# Compaction Evaluation

`bun run eval:compact` measures how well a chosen model works as the Magic Compact summarizer. It runs the real packed `arkive-compact` package inside an OpenCode server you already have running and authenticated, against a frozen synthetic corpus, and records what happened: whether `/magic-compact` delivered a valid successor, what each attempt cost, and, when graded, how many gold facts each summary kept.

The results describe one model, on one host setup, on three synthetic cases. They are not a general accuracy rate for the model and are not comparable with the retention evaluation in `docs/RetentionEvaluation.md`.

## What a run does

For each case and repeat, the eval:

1. creates a fresh source session holding the case's two synthetic turns (the target turn, then an unrelated turn protected by `N = 1`);
2. runs `/magic-compact 1` once, with no retry;
3. checks the successor mechanically against the source's native records as read before the command ran (see Mechanical checks);
4. removes the sessions it created when their recorded state is unchanged.

All sessions live in a private temporary project under the system temp directory, marked with the run's nonce. That project's local config loads the packed package through an eval wrapper (see Isolation), sets the summarizer to `--model`, and disables every MCP server the global config defines. Your global config, your other projects and your existing sessions are not read for content or changed.

Each attempt is one paid summarizer request (`/magic-compact` makes one request per target turn, and each case has one target). The corpus has no tool calls, so task-aware retention has no candidates: no TypeSafe key is needed and no classifier request is made. `check` proves this offline with the production planners and candidate finders for both hosts, and `run` applies the same test before it contacts the server: on both hosts every case must plan one target turn, one preserved turn and no candidate.

## Requirements

- Bun, and npm on `PATH` (used to pack the subject and install the wrapper).
- A running OpenCode server on this machine's loopback interface, with the model's provider already authenticated in that server. Supported servers are OpenCode 1.18.30 and 1.19.0, and OpenCode 2.0.28 (see Host versions).
- If the server uses Basic Auth, export `OPENCODE_SERVER_USERNAME` (default `opencode`) and `OPENCODE_SERVER_PASSWORD`. These are the only credentials the eval reads. Provider credentials stay inside the server; the eval never reads or copies an auth store.

The server must be local because it installs the packed artifact from a path on this file system and writes the run channel into the output directory. A remote URL is refused.

## Commands

```bash
# Offline: validate the frozen corpus and its plans. No server, no network.
bun run eval:compact check

# --out must not exist yet, but its parent must.
mkdir -p runs

# Preflight only: identify the server, load the plugin in the eval project,
# check the model and variant exist. Creates no session, sends no model request,
# but does create its own --out directory, so it gets a name of its own.
bun run eval:compact run --server http://127.0.0.1:4096 \
  --model anthropic/claude-haiku-5-5#low --out runs/haiku-low-preflight --dry-run

# A run: every case twice, no grading.
bun run eval:compact run --server http://127.0.0.1:4096 \
  --model anthropic/claude-haiku-5-5#low --out runs/haiku-low --repeat 2

# One case, graded by an explicit judge model (one extra paid request per delivered summary).
bun run eval:compact run --server http://127.0.0.1:4096 \
  --model anthropic/claude-haiku-5-5#low --out runs/haiku-low-b --case B \
  --judge openai/gpt-6-luna-fast#low

# Grade a finished run later, with a judge or with your own grades.
bun run eval:compact grade runs/haiku-low --server http://127.0.0.1:4096 --judge openai/gpt-6-luna-fast#low
bun run eval:compact grade runs/haiku-low --import my-grades.json

# Offline: summarize and compare saved runs.
bun run eval:compact report runs/haiku-low runs/luna-low
bun run eval:compact report runs/haiku-low --json

# Reconcile an interrupted run and remove what it still owns.
bun run eval:compact cleanup runs/haiku-low --server http://127.0.0.1:4096
```

`--model` and `--judge` take `provider/model` or `provider/model#variant`, using the server's own provider and model IDs. If the server does not list the model, or the model has no such variant, the run refuses before creating anything. There is no fallback model and no default judge.

`--out` must name a directory that does not exist yet; runs never overwrite each other. `--repeat` runs every selected case that many times (1 to 20). A failed attempt is recorded once and is not retried.

Other options: `--cache DIR` overrides the artifact cache, `--subject TGZ` evaluates an already packed tarball instead of packing this checkout, and `--assert-host-version VERSION` runs on an unqualified host version (recorded as operator-asserted).

## Isolation

The eval loads the subject through a thin eval-only wrapper whose package depends on the unmodified packed `arkive-compact` tarball under an alias. The wrapper passes every product hook through unchanged and adds, for one run: a load witness, a record of each Magic Compact command's exact result text, content-free usage numbers, and removal of a successor's omission cache and stats through the subject's own storage functions (see Cleanup and failures). On OpenCode 1 it also sets the summarizer agent's variant to exactly the requested one in that instance's in-memory config, because OpenCode 1 merges agent config field by field: without this, a variant from your global `magic-compact-summarizer` profile would apply to a `--model` given without one. No config file changes. These records go to `OUT/channel/`. The wrapper is test instrumentation, not a product API.

- **OpenCode 1** dedupes plugins by package name, so the wrapper is named `arkive-compact` and is listed as `arkive-compact@file:<cache>/v1/wrapper.tgz` in the eval project only. A globally configured `arkive-compact` stays active everywhere else.
- **OpenCode 2** activates only the first plugin with a given ID, so the eval project negates `arkive-compact` and loads the wrapper directory under the ID `arkive-compact-eval`.

OpenCode 2.0.28 activates a location's plugins in the background when the location is first used. It applies the plugins it can load locally first, the host's built-ins and the eval wrapper among them, so the plugin list is soon not empty; packages it still has to install, such as a global plugin missing from its package cache, are applied after their install finishes or fails. The activation has settled once both batches are applied, and that is the state `session.command` waits for before it runs a command. The plugin, command, agent, config and MCP lists answer from whatever has been applied so far, so a non-empty list does not mean the activation has settled. Preflight therefore first waits on the public `model.default` route (`GET /api/model/default`) at the eval project. On 2.0.28 that read-only route waits up to 5 seconds for the location's plugins to settle, then answers HTTP 503 with a `ServiceUnavailableError` whose `service` is `plugin`. Preflight asks again only after that answer, with no pause between requests and only within 30 seconds of the first request; any other error ends preflight. A project still activating after 30 seconds is refused before any session exists, with nothing read. Once the route answers, preflight reads the project's plugins, commands, agents, config and MCP servers once each, and the judge location is settled the same way before its model and agent are read. A package whose install failed is recorded in `preflight.json` without an ID, as `package:<target> (error)`.

Settlement is a fresh observation, not a lock: a config change or a package update after it can start another activation, and preflight does not notice one. When a global package finishes installing during the activation, OpenCode 2.0.28 sets up the eval wrapper a second time (seen in the qualification containers); preflight then counts two wrapper initializations and refuses. The route's waiting and its 503 answer are OpenCode 2.0.28 behavior (`server/src/location.ts` and `server/src/handlers/model.ts`); check both again before qualifying another version.

Before any session is created, preflight requires exactly one Arkive plugin in the eval project, one wrapper initialization with this run's nonce and artifact, zero differences between the installed subject files and the packed tarball, the three product commands, the summarizer resolving to `--model` with exactly its variant, or none when `--model` names none (both as configured and as the plugin itself reads it), the judge agent resolving to `--judge` the same way, and every inherited MCP server reported disabled by the host. Any failure refuses the run.

Other global plugins, such as auth plugins, and global instructions still load in the eval project, because the eval measures your actual host setup. `preflight.json` records the effective plugin specs, SHA-256 fingerprints of instruction paths, and the provider's model descriptor, never their contents or any secret. Two people running the same model can get different results if their host setups differ.

## What stays behind

- **Run directory** (`--out`): `run.json` (server, corpus, request), `preflight.json` (artifact hashes, effective setup, model descriptor), `results.json`, `attempts/*.json`, `grades/`, `ledger.jsonl` and `channel/`. Capsule text is the synthetic corpus summarized by your model.
- **Artifact cache** (`${XDG_CACHE_HOME:-~/.cache}/arkive-compact-eval/<key>`): one immutable entry per subject tarball and wrapper version, about 14,000 files including the installed subject. Repeated runs of the same artifact reuse it. An entry is built in a staging directory and renamed into place, and it is checked against its own file record before every use. An entry that fails the check is refused and left untouched; delete it to rebuild.
- **Host package cache**: OpenCode 1 installs the named wrapper tarball into its own package cache (`~/.cache/opencode/packages/arkive-compact@file:...`), once per artifact. OpenCode 1 may also install `@opencode-ai/plugin` into its global config directory as part of its normal startup.
- **Host project metadata**: OpenCode keeps its own records of the temporary project (project and snapshot data). The eval does not sweep host databases.

The temporary tree is one root directory (`arkive-compaction-eval-XXXXXX` under the system temp directory, or `arkive-compaction-eval-judge-XXXXXX` for a later `grade`) holding the `inspect`, `project` and `judge` locations. The root and each location carry a `.arkive-compaction-eval` marker naming the run's nonce, its output directory and the root. When nothing the run owns remains, the eval disposes its locations (`instance.dispose` on OpenCode 1, `debug.location.evict` on OpenCode 2, each bound to the eval's own directory), deletes them and then removes the root, which must by then be empty. It never calls a global dispose, reload or upgrade.

## Cleanup and failures

Every session the eval creates is written to the ledger before the request, with its title and, when the host allows choosing one, its planned ID, and again with its returned ID. A session is removed only when a fresh read shows it at its own eval location with exactly the header and history digests recorded for it and no pending work: no running, retrying or unknown status, no child session, and no waiting permission request or question (OpenCode 1), or no activity, queued message, permission request, form or running shell started from it (OpenCode 2). The header digest covers every field that can change the session's behavior, including agent, model, permissions, metadata, sharing, archive and native compaction state, and on OpenCode 2 the session's active instruction entries; only timing and cost fields are left out. Anything that cannot be read, including an instruction entry list, keeps the session. This check is fresh, not atomic: no public API lets the eval exclude another writer acting between the read and the delete.

A recorded state is only ever one the eval knows it produced. A session it created and never prompted must still be exactly as created, with no instruction entries (OpenCode 2.0.28 creates none). A source is recorded from the same read that showed it equal to the corpus and to the header the eval itself created, never to the header that read returned: on OpenCode 1 the header the creation returned, whose title, agent, model and directory must be exactly the requested ones; on OpenCode 2 the session record the eval imported, with no instruction entries, built from a template session whose returned title, agent, model and location must be exactly the requested ones (OpenCode 2.0.28 records variant `default` when none was requested). A source that did not match, including one whose metadata, model, permissions or title another writer changed before that first read, is kept with nothing recorded, and its attempt sends no summarizer request. A successor is recorded (`successor-verified` in the ledger) only from a read that passed every mechanical check, with at least one check, while its source was unchanged; on OpenCode 2 its instruction entries must equal the source's. A successor that fails, or that another writer changed before the eval first read it, is `delivered-invalid` and is kept with its storage, its source and its location. Its source stays because a later `cleanup` can only verify the successor, and remove its storage, against that source: each `cleanup` re-runs every mechanical check from scratch against the source's recorded state, and removes both only once the successor passes. The run and `cleanup` therefore settle each attempt's successor before its source, and keep the source while the ledger still shows that successor as the run's, whatever kept it.

Each scratch root is bound to the server process that created it. Preflight records the process ID (`server-witness` in the ledger) before any session exists: on OpenCode 2 from `/api/info`, on OpenCode 1 from the eval wrapper's witness read live through the eval project's config. A session counts as gone, and a location is disposed, only while that same process answers; a PID read earlier from the channel is not proof.

A successor's cache and stats are removed in two steps. First the wrapper, running a control command inside the successor, confirms the successor is this run's: the request names the run, the successor and its source are in the eval project, the source's title carries the run nonce and the successor's lineage names that source. This writes nothing; the ledger records the wrapper's answer (`storage-receipt`). Then the eval checks the successor like any other session and deletes it, and the wrapper removes the storage only when the host reports that deletion. A successor the eval keeps keeps its storage. A successor that another writer deleted after the wrapper prepared its receipt is recorded as absent, and its storage is settled the same way, because the wrapper also removes the storage for that deletion. When a deletion's storage removal is not confirmed within 15 seconds, the attempt records the storage paths left behind, and the run still owns that storage until a removal is confirmed. A later run disposal, `grade` or `cleanup` records a confirmation the wrapper wrote to the run channel after the eval stopped waiting, but only one for that exact request and successor. The eval never removes the storage itself: once the session is gone only the wrapper's receipt can, so storage whose removal is never confirmed stays reported, with its paths when they were recorded.

A successor that is already gone when the eval comes to remove it, for example because its deletion succeeded but the ledger could not record it, gets no new receipt request, since no command can run inside it. While the server process that created it answers, the eval records it as absent only from a receipt the wrapper prepared for it earlier, read from the ledger or, when the ledger has no answer for that request, from the run channel line for that exact request and successor. That receipt decides which storage removal must still be confirmed. A gone successor with no prepared receipt stays the run's and is reported, because nothing can confirm or remove its storage.

The wrapper keeps one receipt per successor and replaces it with each request it prepares, before it writes its answer to the channel. When that write fails, or a crash comes first, the ledger has no answer for the request, and the wrapper may hold the receipt under it instead of the last prepared request. Until a removal is confirmed, the eval therefore counts the receipt as held under the last prepared request or under any later request with no recorded answer, and settles the storage on a confirmed removal for the exact successor under any of them. `unconfirmedStorage` and the report's `residue.storage` name those later requests as `uncertainRequestIds`. A request the wrapper refused never replaced the receipt and never counts, and a removal line for another run, request or session, or one that reports a failed removal, settles nothing.

The eval disposes nothing while the ledger leaves anything open: a session not yet removed, a session intent whose creation was never confirmed or ruled out, an attempt whose command started without a recorded outcome, including after a crash that wrote nothing more, or a removed successor whose storage removal is not confirmed, since disposing the project location would unload the wrapper that holds its receipt. This applies to the whole run: anything open anywhere in the ledger keeps every root, the judge roots of later `grade` runs included. It also keeps the tree when any root or location fails its marker check (a missing or different marker, a symlink, a path outside the root), when the host still lists any session at an eval location (for example a candidate the product kept after a failure), or when the root holds files the eval did not create. Sessions it cannot account for are reported, never deleted. A root that a disposal keeps, for one of these reasons or because the run still owns something, is reported as unresolved ownership with the reason and any sessions the host listed, not as something the run owns, so it does not block a later disposal that checks the markers and the session list again. It stays reported until a later disposal removes the root or `cleanup` finds it gone.

If a command's HTTP response is lost, the attempt waits up to 15 minutes for the command's own outcome on the run channel, then records `outcome-unknown` and starts no replacement. Ctrl-C stops new attempts, lets the current one finish and clean up; a second Ctrl-C exits at once. In both cases, run `cleanup` later. It settles attempts from outcomes that reached the channel late, registering a delivered successor first; an attempt with no outcome keeps all of its sessions, including its source, because on OpenCode 2 the summarizer runs in a separate session and an idle source does not show it has finished. It reads a session whose planned ID was recorded, and looks for a session with the recorded title at the eval location when the ID was not. A successor known only from a late outcome is removed only when its source is unchanged since the run recorded it and the successor passes every mechanical check against it; otherwise it is kept. `cleanup` exits non-zero while anything stays, including unconfirmed successor storage (`unconfirmedStorage` in its result) after the session itself is gone. That includes a scratch root that still exists but no longer proves it is the run's (its marker is missing or changed, or something else sits at its path): `cleanup` deletes nothing there, names the root and the reason in its result, and keeps reporting it. Only a root that is gone counts as cleaned.

The ledger is append-only JSON lines, numbered from 1. `grade`, `report` and `cleanup` refuse a ledger before they contact any server, and without changing it, unless every line is a complete JSON object with a kind, a time and a positive safe-integer number above the one before it. Numbers may skip: an earlier version of the eval numbered an entry before writing it, so an append the file system refused left a gap before the next entry. Such a ledger is valid as it is; entries refer to each other by number, so nothing is renumbered, and the next entry takes the number after the highest one. That earlier version also restarted from the line count when a later command opened a ledger, so after a gap it could write a number that already exists. A ledger with a repeated number is refused: a reference such as `intentSeq` to that number could name either entry, and renumbering would change what it names. Review such a ledger by hand. A last line cut short by a crash is refused rather than dropped or renumbered, because the cut entry may record a session the run created: review the file and repair it by hand. Before each append the eval checks that the file still has the size it last read or wrote, and refuses to write otherwise. That check notices another writer that already acted, but it is not a lock: do not run two eval commands against one run at the same time.

A run writes `run-start` with its nonce as the first ledger entry, before `run.json` and before anything it creates, and every version of the eval has done so. Only a ledger that begins that way can show everything the run owns. A judge `grade` adds a scratch root and judge sessions to what the run owns, so it refuses a run whose ledger is missing or begins any other way, before it contacts the server or writes anything. `grade --import` and `report` still read such a run when its attempts pass saved-run validation (see Scoring): every session an attempt names needs a creation record for that attempt in the ledger, so an attempt that names a source or successor is refused when the run has no ledger or only one an earlier `grade` began. `cleanup` refuses a run with no ledger before contacting the server, because it has nothing to reconcile. An earlier version of `grade` started a new ledger for a run that had none, beginning with its own `scratch-root`. That ledger records only what that `grade` did, so `report` lists its residue but marks ownership incomplete (`ownershipKnown: false`), and `cleanup` settles what it recorded but never reports the run complete. Nothing in it is deleted, renumbered or rewritten.

`grade` and `cleanup` work only against the server the run used. `--server` must be exactly the URL in `run.json` (`server.url`); another URL is refused before anything is sent, even another name for the same address such as `localhost` for `127.0.0.1`. `cleanup` then compares the live process ID with the one each root recorded. When it differs, for example after the server restarted or when another server took over the port, `cleanup` keeps every session and location of that root, marks nothing absent and exits non-zero. It never reads a host database directly and has no override: restart the original server process if it is still available, or review the kept sessions by hand. A root whose process was never recorded is disposed only when the run created no session in it, which happens when preflight stopped before identifying the server. A `grade` run on OpenCode 1 records no process ID for its judge root, because no eval wrapper loads at the judge location, so a crashed OpenCode 1 `grade` leaves its judge root for manual review.

Attempt statuses are `delivered` (every invariant passed), `delivered-invalid` (a successor exists but an invariant failed), `noop`, `failed` (with a category: capability, provider, schema, coverage, savings, setup or other, plus the exact command text), `outcome-unknown`, `preflight-skipped` (for example an image case on a model without image input) and `setup-failed`.

## Mechanical checks

A delivered successor must be exactly the source as `/magic-compact 1` defines it, compared field by field on the hosts' native records. Every user message, with every native field, file part, file name and metadata, and the protected second turn, with its parts, finish and metadata, must equal the source's. The summarized assistant message keeps its own fields and holds only the v3 capsule (on OpenCode 2 its metadata gains only the capsule's `magicCompact` entry). The only additions allowed are Magic Compact's own: the boundary text leading the next user message (a boundary record before it on OpenCode 2) and, on OpenCode 1, the ignored stats notice after the history. The only differences allowed are fresh message and part IDs, which must be unique and absent from the source, the links between them, the session they belong to, the boundary's creation time, and the capsule and stats text. The successor's header must carry the source's title, agent, model, permissions and location, its metadata plus the lineage entry, and nothing else. A record added, dropped or changed anywhere else makes the attempt `delivered-invalid`.

## Scoring

The rubric is `packages/opencode-plugin/eval/compaction/corpus/v1/scoring.md`, frozen with the gold facts before any model was run. Each case has 8 text facts, 4 of them critical; cases B and C also have 4 visual facts. A summary scores one point per fact it states correctly, minus two per distinct false assertion in that dimension, floored at zero. It is usable when every critical fact is present and no false assertion is critical.

Under the rubric, an attempt that settled without a valid summary (`failed`, `noop`, `delivered-invalid`, or `preflight-skipped` because the model cannot take the case's image) scores 0 in every dimension and is not usable. An attempt whose outcome is unknown, or that never reached the model (`outcome-unknown`, `setup-failed`), is not scored at all and is counted separately. Per-case means and usable rates are taken over graded and zero-scored attempts. A delivered summary without an accepted grade is never counted as 0: while any summary of a case is ungraded, that case reports `PARTIAL` and no mean. For example, a case with one summary graded 8/8 and one provider failure has a mean of 4/8 and is usable in 1 of 2 attempts. When no attempt delivered a summary, every settled attempt scores 0 without a grader.

Without accepted grades, the report says `Semantic: UNGRADED`. Mechanical success says nothing about summary quality. Partial grades are reported as `PARTIAL`.

Grades are always per-fact judgments; the eval computes every score itself. A grades file (`arkive-compaction-eval-grades/1`) is bound to one run's nonce, the corpus and rubric hashes, and each attempt's case and capsule SHA-256. Each item judges every gold fact of its case exactly once (`present` plus an exact quote from the summary as `evidence`) and lists false assertions with their dimension, criticality, claim and quoted evidence. A file that names another run, case or output, repeats an attempt, or quotes evidence that is not in the summary is rejected as a whole. To grade by hand, copy an existing judge grades file from `grades/`, set `grader` to `{"kind": "manual", "label": "<your name>"}`, edit the judgments, and import it.

`grade` and `report` first check the saved run itself and refuse it as a whole when it does not match this checkout's corpus and rubric, or when an attempt record names another run's nonce or another requested model, names a source or successor the run's ledger did not create for that attempt, names a case or repeat the run did not request, has an unknown status, or holds a summary whose SHA-256 differs from its recorded digest. An intact attempt file copied from another run therefore fails before any grade, report or judge request. The digest is recomputed from the saved summary, so an edited summary cannot keep an earlier grade. A run directory without a ledger is still read, but none of its attempts may name a session.

A report names what the run still owns now, derived from the ledger: sessions whose removal is not settled, with the reason they were last kept, removed or vanished successors whose storage removal is not confirmed, session creations neither confirmed nor ruled out, and attempts with an unknown outcome. `report --json` gives these as `residue`, and keeps `cleanupRetained`, the IDs of the sessions whose removal is not settled. Separately, it lists scratch roots kept as unresolved ownership (`unresolvedOwnership`). `ownershipKnown` is true only when the ledger is the one the run wrote. For a run without a ledger, what it owns is unknown rather than none, because a session creation that failed before its ID returned leaves no ID in the attempt record: `residue` and `unresolvedOwnership` are `null`, `cleanupRetained` is empty, and the report says that ownership is unknown. Attempt records keep the cleanup results of their own time and are never rewritten, so a report made after `cleanup` no longer lists what `cleanup` removed.

A judge model receives a blind packet: the case's frozen source text (with the image described by its gold facts), the gold facts and the summary, with no model, run or cost information. It runs in its own temporary location with every tool denied, and answers in plain text on both hosts: the prompt asks for one JSON document matching a JSON Schema generated from the judgment schema that then parses the answer (the same shape as a grade file item), and the answer is parsed strictly with no repair. A malformed, missing or refused answer is recorded as a judge error and leaves that summary ungraded; it is never scored as zero. Judge scores are labeled as automatic estimates from one model, separately from manual grades.

A judge session is removed only while it holds exactly what the eval put there. On OpenCode 1 that is the prompt, sent under a user message ID the eval chose, and the finished reply the host returned for it; a judge session holding anything else is kept, and its answer is a judge error because the judge saw more than the blind packet. On OpenCode 2, `session.generate` writes no history, so the session must still be empty and unchanged since its creation.

## Host versions

The eval identifies the server from JSON, not from an HTTP 200: OpenCode 1 must answer `/global/health` with a `1.x` version and OpenCode 2 must answer `/api/info` with a `2.x` version and process ID. It records the canonical URL, the version the running server reports (not the binary on `PATH`) and, on OpenCode 2, the process ID.

Qualified versions are OpenCode 1.18.30, 1.19.0 and 2.0.28. Their plugin loading, wrapper route, MCP disabling, session lifecycle and location disposal were checked in scripted containers. Any other version is refused, because a different loader or session API could load the wrong plugin or misjudge ownership. `--assert-host-version` lets you run anyway; the run is then recorded as operator-asserted.

Known limits:

- **OpenCode 1 judge format.** OpenCode 1.18.30 cannot return the history of a session that holds a JSON-schema prompt, so the judge never uses the host's structured response format; it answers in plain text, which keeps its history readable for the ownership check.
- **MCP on OpenCode 2.** OpenCode 2.0.28 ignores a partial `{disabled: true}` override, so the eval project replaces each inherited server name with a complete disabled stub. The stub copies nothing from the inherited definition.
- **Plugin settlement on OpenCode 2.** Preflight relies on 2.0.28's `model.default` route waiting for plugin settlement and on its 503 answer (see Isolation). Another version may change either, so check them before adding it to the qualified list.
- Only loopback servers are supported.

## Corpus versions

`corpus/v1` (`magic-compact-synthetic/1`) holds three cases, promoted from the 2026-10-15 summarizer comparison. A is a text-only rate-limiter fix, B is a timestamp fix plus a 512x512 red-left, blue-right PNG, and C is a CI Node upgrade plus a two-row status table PNG. Case B's image was used in earlier diagnostics and is not held out. `manifest.json` binds every corpus file by SHA-256, and `provenance/comparison-manifest.json` binds the texts, gold facts and image bytes to the original frozen fixtures. Corpus files are data; the eval never imports or executes them, and it refuses unknown formats, extra fields and hash mismatches.

To add or change cases, create a new corpus version directory with its own manifest and corpus ID. Never edit a frozen version or regrade old runs against changed gold facts: a run's grades are only accepted against the corpus and rubric hashes it ran with.

## Maintenance

`packages/opencode-plugin/test/compaction-eval.test.ts` owns the offline invariants: corpus integrity and its retention-free plans, server identity, model selectors, preflight refusals, OpenCode 2 preflight and judge reads waiting for plugin settlement through the public client (asking again only after the host's plugin-activation answer, and refusing at the deadline), the summarizer variant override, artifact cache reuse and tamper refusal, the mechanical checks against successors the production command produced and against native successors captured in qualification containers (`eval/compaction/testdata/`, recapture them when a qualified host version changes), ownership-checked removal and successor storage removal, verified-only removal baselines (an end-to-end OpenCode 2 attempt with the production command, and source headers checked against what each driver created), server process binding, both host drivers' pending checks, instruction entries and judge ownership, ledger integrity (including a gap an earlier writer left) and its append check, ledger reconciliation, unconfirmed successor storage and its late confirmation, a successor deleted by another writer after its receipt, a receipt request whose answer the channel refused, a successor removal the ledger could not record settled by the next `cleanup`, the successor-before-source order of each attempt, scratch markers, saved-run validation, the current residue and unresolved ownership in reports (unknown without a ledger, incomplete with a ledger the run did not write), judge grading refused before any request when the ledger is missing or one an earlier `grade` began, `cleanup` refused before any request when the ledger is missing and, with an earlier `grade`'s ledger, settling what that ledger recorded while ownership stays incomplete, the judge schema generated from the answer parser, and grade binding and scoring. Re-qualify in containers on every supported host when the wrapper, the host drivers or the qualified version list changes.
