# Magic Compact Core

Source of truth for Magic Compact behavior and safety guarantees.

## Goal

Compress a conversation without flattening it into a single generic recap.

## Core Behavior

- `/magic-compact [N]` compacts the current conversation into a new successor session and leaves the original session unchanged.
- `N` keeps the most recent eligible complete request turns unchanged. A request turn is one or more adjacent user messages plus every following assistant and tool step until the next user request. Default: `0`, which includes the most recent complete turn in compaction.
- We also provide `/magic-trim [N] [--heuristic]`, which applies tool I/O trimming without summarizing assistant turns.
- Compact and trim never write the original session or its subagent sessions. Each successful run creates one verified root successor session with fresh session, message, and part IDs, copies the original's continuation state (agent, model and variant, permission rules, metadata, directory, workspace, title; on OpenCode 2 also the active instruction entries), and names its ID in the result. A run that changes nothing creates no successor.
- When a successor is ready, every TUI with the plugin that still shows the original session opens it, whichever terminal or headless client ran the command; TUIs showing other conversations are left alone, and the original stays available.
- A command runs only on a root session at rest: no running model response or tool call, no busy, retrying, or unknown session state anywhere in its subagent tree, no pending permission request or question, no running native compaction, and no pending revert. The complete source and its continuation state are read again before the successor is marked ready, and any difference discards the unready successor. This detects concurrent change; it is not a lock. Within one plugin process a second command for the same source is refused while the first runs.
- The commands use only OpenCode's public HTTP API and require an endpoint that proves it belongs to the same OpenCode instance before any read or write: on OpenCode 1 a listener that returns this process's identity value, on OpenCode 2 the registered service or the configured `serverUrl` when it reports this process's ID and the same source session.
- One package serves OpenCode 1 and OpenCode 2 with one policy: turn grouping and ranges, tool rules, task-aware retention, the generation protocol and strict response validation, budgets, profitability and the savings gate. Each host adapter maps its native records onto that policy and applies the resulting edits to clones of its own records; no host's records are converted into the other's. OpenCode 1 and OpenCode 2 sessions keep separate omission caches and stats, and nothing is migrated between them.
- Summary generation, per-turn compaction, and successors share one chronology-preserving history replay. Stored source order is authoritative. OpenCode 1.18.30 mints a native fork's message and part IDs one record at a time from the host clock and reads parts back in ID order, so a host clock that steps backwards during the copy, or JSON message creation times that disagree with the host's row ordering times, can reorder a valid history. No fork is populated by that copy. Every fork is an empty native fork cut before the first planned message, and the planned history is written once through host replay with IDs minted from a single clock reading, ordered row keys, and the exact original JSON timestamps restored. Every fork reload must preserve rewritten record identity, roles, parent and checkpoint-tail links, ordered parts, and content. The source is never repaired or rewritten by this process.
- User-authored message parts are preserved exactly. Original user file parts and assistant inline image file parts covered by an accepted v3 manifest are never updated, deleted, moved to omission storage, or replaced in persistence, successors, API responses, or exports.
- Older assistant turns are replaced turn-by-turn with validated continuation summaries, not merged into one blob.
- Compaction resolves the model and variant the operator configures on the plugin-owned `magic-compact-summarizer` agent, as configured for the source session's own project, and the matching live provider descriptor once; neither the source session model nor OpenCode's native compaction agent is ever a fallback. The output target is `min(32K, floor(model output * 0.5))`, usable input is `min(model input when present, context - output target)`, the normal target is `min(400K, floor(usable input * 0.8))`, and the hard single-turn limit is `floor(usable input * 0.9)`. Every batch reserves 8K only for non-explicit host, system, and provider overhead. It separately tokenizes the complete rendered explicit request exactly once, including static instructions, the repeated global index, target JSON and punctuation, conservative marker and marker-injection text, exact ordinals, and media counts. Each batch carries exactly one target turn, so the fixed request parts, global index, and any preceding halo turn repeat across requests.
- Ordinary model-visible text and reasoning are estimated with the local tokenizer without serializing SDK message objects. Image/PDF-typed file parts and completed non-compacted tool `state.attachments` receive fixed 8K media charges; `text/plain` and directory file parts are non-model-visible and carry no charge, and other model-visible file parts and attachments are estimated by their URL (encoded length for `data:` URLs, tokenized text otherwise). Arbitrary or nested `data:` strings in tool input, completed output, errors, and model-visible interrupted `state.metadata.output` remain ordinary provider-request text and are estimated conservatively by encoded length without invoking the tokenizer on their payloads. Compacted tool output becomes OpenCode's fixed cleared-result text with no attachments; other error, interrupted, pending, and running states mirror the pinned native conversion. Output packing adds estimated summary and visual-description content to the mandatory JSON envelope/array/object punctuation, echoed marker/ordinal fields, `summary` property, and every visual-description ordinal/description record. Every candidate gets its own batch in chronological order without splitting turns. A turn above the normal target retains the hard single-turn limit; an impossible turn fails before backup with `/magic-trim`-first guidance.
- Before batching, Magic Compact derives one immutable `globalTurnIndex` from every complete turn in the effective source history after the newest native checkpoint. It includes target, opaque existing-summary, and retained-tail turns; excludes an active incomplete turn; and gives each entry only `{sourceOrdinal, anchor}`, where `sourceOrdinal` is the stable one-based position in complete source-turn order and `anchor` is the first ordinary user line capped at 160 characters.
- Each batch directly awaits a fresh ephemeral fork of the complete source without a local wall-clock deadline and then installs an ordered session rule that denies operational tools and allows only the injected `StructuredOutput` response tool under the control deadline. Magic Compact verifies rewritten IDs and chronological role/part-type shape, retains only the complete target turn plus at most the one complete preceding non-checkpoint turn while native history plus the complete explicit request stays within `min(500K, floor(usable input * 0.9))`, and captures the retained rewritten message IDs, part IDs, order, roles, parent links, part types, and fork-scoped references before deleting every other fork message sequentially through `session.deleteMessage`. It never deletes individual parts for generation isolation. The reload must match that exact retained identity before the unique nonce-bound target marker is inserted. Later turns, including turns protected by `N`, never enter a generation request; they appear only as user anchors in the global map and stay unchanged in the successor.
- OpenCode supplies retained fork user, assistant, tool, reasoning, and media history through native model conversion. Every prompt receives the byte-identical global orientation map plus a separate exact target index of marker, target ordinal, and expected inline-image count; target entries carry no user text. The global map gives long-range user-anchor orientation only. Its anchors never identify response items, and it carries no distant detailed assistant/tool history. SDK objects, source refs, assistant traces, tool states, data URLs, provider metadata, encrypted reasoning, and manual file parts never enter either index.
- One structured-output response per batch contains exactly one object for the batch's single indexed target. OpenCode captures the JSON-schema response on assistant `info.structured`; Magic Compact does not parse text parts. The fixed schema sets `minItems` and `maxItems` of the `turns` array to 1, the prompt states the same count, and the schema JSON is charged to every explicit request budget. The schema guides the model; OpenCode does not validate tool arguments against it, and OpenAI-family providers receive it non-strict. The mandatory envelope and every echoed marker, ordinal, `summary` field, and visual-description record are included in output packing before estimated content. Local validation treats the captured object as untrusted: every object must have exactly `ordinal`, `marker`, `summary`, and `visualDescriptions`, echo its exact nonce-bound marker token and target ordinal in batch order, and include a nonempty summary plus exact visual coverage. Response identity is the exact result count and order, ordinal equality, and marker equality; it never requires the model to echo user text. Missing or extra keys, and missing, stale, spoofed, shifted, duplicate, reordered, empty, or active-nonce values, fail before a successor is created. All batch results and exact target-ordinal coverage are validated atomically before any durable write.
- Accepted v3 summaries persist a version-1 manifest built locally from authoritative source user then assistant inline image parts, binding stable encounter ordinal, exact MIME, and SHA-256 of the exact original URL. Tool `state.attachments` remain native tool media and never enter this persisted manifest. OpenCode's `experimental.chat.messages.transform` hook applies one pure projection that validates every manifest-covered historical image by canonical ordinal/MIME/hash and replaces it with a lightweight declarative text placeholder only when the placeholder's canonical token count is strictly smaller than the original file URL token contribution; otherwise the exact file part stays inline and model-facing. Persisted v2 manifests remain user-only and supported, but their stored `partId` is compatibility data and does not block a content-identical fork or successor with rewritten IDs. Missing manifests are inert; missing/added/reordered images, malformed manifests, MIME changes, or URL-hash changes fail closed instead of hiding or silently resending changed media. Because every replacement strictly reduces canonical tokens, projected media token counts are non-negative by construction. On OpenCode 2 the manifest binds the inline user images OpenCode sends by ordinal, MIME and SHA-256 of the exact stored base64 data, and the `context`, `compaction`, `generate` and `title` hooks apply the same pure projection to every request; profitability, the savings gate, verification and stats use it too.
- Host-injected text in a summarized turn follows one rule on both hosts: user-run tool notices, task and subagent results, working-directory changes and user comments stay exactly; other transient host reporting is dropped. On OpenCode 2, shell and subagent notifications always stay and records that carry session state (skills, user shell runs, switches, system notices) are never dropped.
- Useful tool calls stay visible; bulky tool I/O is replaced with retrievable omission records.
- Each omission leaves one compact recovery reference carrying its Content ID, in the field it replaced: a replaced input holds its own reference (`[Omitted; Content ID: ...]`, an edit's two fields sharing one entry, a command's first 512 characters followed by a truncation reference, a task prompt's `[Historical task prompt omitted; ...]` placeholder), and a replaced output holds its byte size, plus the native child session ID for a long subagent report when the host reports one. Output text is never changed when only an input is omitted. Retrieve the original before reuse; a reference is not a new assignment. Histories trimmed earlier keep their XML notices, bare `[Omitted]` inputs and long task placeholders unchanged. Read omissions recover the exact captured result; reread files when current contents are needed.
- Task-aware retention adds a keep veto to the existing tool rules in both `/magic-compact` and `/magic-trim`. Candidates are exactly the completed tool parts in the command's eligible turns whose model input or output the existing rules would change; a part whose trim would only stamp its trim marker is not a candidate. With no candidates, no summary or TypeSafe request is made. Otherwise one fresh whole-session summary is generated through OpenCode's native compaction agent and never appended to the source. TypeSafe Jev (`jev-1.13.0`) judges whether the assistant would likely use concrete input or output again for the current task, independently of duplication or recoverability. Still-relevant task procedures and useful unchanged content in partly edited reads qualify. A candidate is kept whole only at probability >= 0.80; uncertain candidates follow the existing rules. A kept part stays byte-identical, including its input, output and trim metadata. Keeps have no size cap, persistent pin or automatic restoration; decisions are recomputed on the next run. The threshold was selected on development sessions before held-out inference; measured results and limitations are in `docs/RetentionEvaluation.md`.
- Kept parts count as retained content in every per-turn profitability check and in the aggregate savings projection. Retention never drops a keep to reach a savings target; a keep can leave its turn unsummarized or fail the savings gate.
- Trim's ignored outcome notice adds one retention line matching terminal feedback, for example `Retention | Task-aware retention kept 4 of 9 evaluated tool call(s) whole (read 4).` It counts evaluated candidates only and lists at most three kept tool names, sorted by count then name, plus remaining call count. Labels are capped at 24 characters with controls/whitespace collapsed; arguments and content are never included. Zero keeps, no candidates and heuristic non-evaluation are explicit. No-op results remain toast-only.
- Any missing `TYPESAFE_API_KEY`, summary, budget, fork, provider, response-shape, classification, or missing-decision failure fails the whole command before a successor is created, with no partial decisions, and suggests `/magic-trim --heuristic`. `/magic-trim --heuristic` skips retention entirely and makes no model or TypeSafe request.
- Omitted bytes are returned only when OpenCode can authorize the current session and prove cache integrity; unavailable or ambiguous historical entries fail closed.
- Any turn containing an existing Magic summary part is opaque persisted data for the compaction writer. V0, v1, and v2 turns are skipped message- and part-identically, while the normal boundary allows newer turns to compact safely. `/magic-trim` leaves the summary parts themselves unchanged. New summaries use the versioned v3 part ID namespace only on summary-free turns.
- During `/magic-compact`, a completed OpenCode-native checkpoint owns an immutable durable prefix. Compaction processes only completed turns after that checkpoint summary.
- If the native checkpoint leaves no eligible turns, compaction is a no-op and creates no successor or summary request. `N` can also swallow every eligible turn; success and no-op feedback then state how many whole request turns `N` preserved, and a preserved turn can hold most of the active context.
- Before creating a successor, Magic Compact projects the complete canonical model-facing result with local `gpt-tokenizer` counting and the same pure media-manifest projection used by the OpenCode hook. Model-facing synthetic content is included; ignored user reporting notices are excluded; ignored assistant text stays in the active count and source projection. Attempts below 20% of eligible removable tokens, subject to a small absolute floor, fail unchanged with a content-free failure message.
- A planned turn is replaced only when its exact projected canonical active token count, after injecting its summary and applying the same planned pruning, is strictly lower than its exact source canonical active token count. Rejected turns stay message- and part-identical: no summary is injected and no pruning is applied to them. The aggregate savings gate evaluates the eligible token base over only the selected profitable turns, and its projected savings already net out the fixed model-facing boundary.
- `/magic-stats` shows cumulative savings for the current conversation.
- `read_omitted_content` retrieves omitted tool content by Content ID and returns the whole original from the cache. The tool description, shared by both hosts, explains the references once instead of each reference repeating it: exact capture, OpenCode may truncate a large tool result and provide a reference to the full output, historical not current, retrieve a task prompt before reuse, and current-session scope (including entries copied into a successor). The post-compaction notice is unchanged.
- `/magic-compact` and `/magic-trim` show a long-lived view-only progress toast before slow work and then send terminal no-op, success, or failure feedback. If a timed-out progress delivery later settles, Magic Compact best-effort reasserts the terminal toast. Progress feedback never appends conversation history, reaches model input, changes stats, or creates omission-cache entries.

## Safety

- Independent batches run with a maximum concurrency of five. Every prompt, index, fork isolation plan, and estimate derives from the same pre-generation source; generated summaries never feed another batch. Fork creation and provider requests have no local wall-clock deadline, so the command retains ownership of every server-side generation fork. The ordered session rule denies operational tools with a wildcard and then allows only the exact `StructuredOutput` response tool. OpenCode 1.18.30 injects that side-effect-free host response tool for the JSON-schema request and resolves the final model tool map through the merged agent-and-session rules, where the last matching rule wins, so the trailing allow keeps the host response tool while every operational tool stays denied. Permission updates, message deletion/reload, marker insertion, and toast delivery use the 30-second control-operation deadline. Provider or validation failure directly awaits an abort attempt, and every known generation fork is directly deleted before its worker settles. The first provider, throttling, validation, lifecycle, or cleanup failure stops new admission; every already-active batch is drained and every active failure is collected in deterministic batch order. One sanitized error or sanitized aggregate is thrown, every generated result is discarded, and no successor is created because generation completes before successor creation. Magic Compact makes one `session.prompt` call per fork and adds no plugin-level provider or model retry or fallback; OpenCode may apply its runtime provider/transport retry policy or additional model steps required by structured-output processing. No partial batch result is accepted.
- The image capability gate covers content retained by any planned fork. Native context overflow reports `/magic-trim`-first guidance. A configured model input budget too small to fit the fixed 8K non-explicit host reserve, or too small for that reserve plus the complete explicit request and mandatory global index, fails before any fork with concise trim-first/model-capacity guidance. Planning uses a fixed-shape conservative nonce; each real nonce and exact immutable prompt are rendered and checked against the recorded estimate plus normal, hard, halo, usable-input, and output limits before fork creation. Output exhaustion requires a compaction model with more output capacity, because every request already covers a single turn. Raw provider/control/model messages, bodies, prompts, histories, output, and aggregate causes are never surfaced. Magic Compact does not adaptively repartition, switch models, or accept partial source mutation.
- Malformed authoritative user or assistant inline-image data, missing or misordered visual descriptions, projection mismatch, and every other media validation failure occur before a successor or stats are created. No media path falls back to another model or provider.
- A successor is marked ready only after fresh reads show its complete continuation exactly as the command wrote it: session record, history and, on OpenCode 2, active instruction entries. A successor that fails before it is marked ready is deleted, with its caches and stats, only when fresh reads show nothing but what the command wrote and no child session, activity or pending request. A candidate someone else changed, one with its own work, one that cannot be read, or one whose ready update may already have applied is kept and named in the error. These are fresh checks, not locks; neither host offers compare-and-swap. No failure writes the original session or its stats.
- Successor failures carry a fixed message, the stage, a fixed category raised by the plugin itself, an HTTP status from 100 to 599 and a known system error code when present, and the source and kept candidate IDs. No host error, body, path or arbitrary code is attached or repeated.
- A fork whose persisted chronology or rewritten content cannot be verified never becomes a generation input or a successor. Present assistant parent and compaction-tail references must resolve to preceding messages. Dangling, forward, self, and empty references, and source records with a foreign session, duplicate message or part IDs, foreign part ownership, or an unsafe creation time, are rejected from the planned history before the host is touched. Before returning any fork, including one for an empty history, Magic Compact reloads the live source and requires normalized structural correspondence with the planned history, rejecting appended or changed content even when trim skipped retention. Timestamp churn is normalized only for this source comparison; the replay's exact persisted timestamps and order are still verified separately. Failed population or verification directly awaits partial-fork deletion before settlement. A replay or cleanup failure leaves source content unchanged; no plugin code writes the OpenCode database directly.
- Every fork-boundary history read (the empty-cut check, the replayed reload, and the live-source recheck) is attempted at most twice, each attempt under its own full control deadline (30 seconds by default, so at most 60 seconds per read). Only a timed-out or rejected request, including an error response, is retried, once and without delay; a response that arrives and fails validation is final and never re-read. Fork creation, replay, partial-fork deletion, and model requests are never retried, and planned history is never refreshed. Failures name one fixed content-free reason, never a host body, path, ID, or value: `history read timed out`, `history read failed`, `history read returned invalid data`, `fork was not empty`, `history replay failed`, `replayed fork did not match the plan`, `source history was invalid`, `source history changed`, or `host returned an invalid fork`. The reason appears in the surfaced error of generation, retention summaries, and backups, and survives a failed partial-fork deletion.
- The retention summary fork is owned by the running command. Its session rule denies every tool and it is prompted exactly once with an explicit message ID. While it is owned, the plugin's native compaction hook throws for it, so OpenCode never sends a native compaction request, replays the prompt, or auto-continues on the fork, whether compaction was triggered by a finished step's token count or by a provider context overflow; the command then reports that the session is too large. The pre-fork estimate and image-capability gate cover the exact pinned native `filterCompacted` membership and order, including its last-tail-marker reorder for errored or unfinished summaries; an estimate above the configured compaction model's hard input limit fails before the fork. This pure accounting view accepts native incomplete/error paths independently of the compaction writer's strict checkpoint checks, but rejects a selected tail that cannot resolve before its marker. A provider error on the prompt response is a provider failure, and a context overflow there or a native compaction marker or summary in the fork is reported as the session being too large. The result is accepted only when the fork is the rewritten source history plus exactly that prompt and one finished, error-free, non-summary compaction-agent reply; any replayed prompt, follow-up, or tool call rejects it. The fork is always aborted on failure and deleted, and its IDs never identify kept parts.
- A pending revert is an at-rest refusal for both commands. Users restore the undone messages with `/redo` or let a normal OpenCode prompt commit the discard, then retry.
- Cache-read diagnostics must not expose local filesystem or session paths. Integrity diagnostics may retain path-free validation detail.
- Toast delivery is best effort and bounded. A rejection or timeout cannot change the command result. OpenCode exposes no later delivery signal after the client promise rejects, so Magic Compact cannot detect and correct a progress toast that the host applies after such a rejection.
- During `/magic-compact`, malformed, ambiguous, dangling, or active incomplete native checkpoint state fails before generation. An older incomplete or ambiguous marker may remain only when its complete ambiguous or incomplete artifact set lies wholly before a later valid checkpoint marker and is inside that checkpoint's frozen prefix.
- Prompt instructions require each summary to remain readable and continuation-focused: preserve the outcome, important process and decisions, verification, and unresolved or next work when present. The host validates only the small structural response contract, not brittle semantic status, evidence, ref, current-state, preserve-mode, or visible-scaffolding protocols.
- Visual descriptions are model output that nothing checks against the image. Validation covers their count, order and nonce exclusion, and the manifest binds the image cohort by ordinal, MIME and hash; neither establishes that a description is accurate. Once a summary is accepted, later model requests carry its description and, where projection applies, a placeholder instead of the image, so an inaccurate description can mislead later turns even though the original image stays stored in the original session and the successor. `read_omitted_content` recovers omitted tool I/O, not images or the assistant prose a summary replaced. Magic Compact does not resize images, validate perception, or retry with another model; description quality depends on the summarizer model and variant the operator configures. Live observations are recorded in `docs/Development.md`.

## Stats

- Track net tokens physically pruned, inline-image tokens projected out per model request, their separate cached-read savings, and estimated money saved per conversation. Existing version-1 stats without media fields remain valid and read as zero media savings. Before, projected-after, and actual-after model-facing counts use the same pure media projection plus local `gpt-tokenizer` canonical active-content method: model-facing synthetic parts are included and ignored reporting notices are excluded. Compaction and trim compute the exact pre-notice stored result once, persist savings on that basis, and require the final actual stored count to equal the projection. There is no self-referential fixed point. Gates, profitability, physical stats, the ignored notice and that final equality all use these stored-history counts, labelled `Stored history (estimate)`. They include any prefix a completed native checkpoint hides from the model, so on such a session they can exceed the request OpenCode sends; they remain canonical estimates, not the model request size or provider usage. Trimming hidden tool output lowers them even though the request is unchanged. The notice also reports the operation kind (summarized request turns or trimmed tool calls) and, for compaction, the whole turns `N` preserved. The `/magic-stats` notice continues to distinguish canonical estimates from provider context-window usage; compact and trim notices report canonical counts of the stored history. Each successor carries the original's cumulative totals forward and adds its own reduction; the original's stats are unchanged, and the totals describe the working conversation, not disk use. OpenCode's context meter is a provider usage snapshot; in a successor it can show the copied last response's usage until a later assistant response refreshes it. Magic Compact never fabricates an after-provider count or mutates provider token metadata.
